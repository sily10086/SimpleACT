# 步骤 01｜冻结实施范围与战斗规则

版本：v0.1｜阶段：S0｜状态：方案已编写，实施未开始。

> 本文属于已授权的文档细化。所有新增类型、接口及路径是拟实施方案；伪代码用于表达控制流，不是可直接编译的代码。执行本步前确认该批次；完成后填写实际记录。

## 1. 目标与需求

把影响后续代码结构的选择形成可追踪的实施基线，让程序知道哪些是已确认要求、哪些仍只是建议。目标是完成一次可实施的批次定义。

- **R1**：记录平台、2D/3D、动画后端、输入设备、同屏单位及弹丸预算，不填没有依据的性能承诺。
- **R2**：明确 StandardActDemo 或 SimpleACT、互击语义、退款、Buff 时间域和确定性等级。
- **R3**：批次确认与具体数值确认分开；未确认的演示参数仍为提案。

## 4. 具体执行任务

### 01.1 确定首版使用场景

- [ ] **做什么**：确定首版使用场景。
- **为什么**：不同平台与动画后端会改变运动和资源实现。
- **怎么做**：以单机 2D Sprite 练习场作为推荐，逐项记录用户决定；数量预算保留待定，不擅自填写。
- **关键伪代码**：

```text
profile = { platform, backend, inputDevices, unitBudget, projectileBudget }
RecordDecision(profile, confirmationSource)
```

### 01.2 冻结裁决与时钟契约

- [ ] **做什么**：冻结裁决与时钟契约。
- **为什么**：同帧互击、时停和回放目标不能留给各模块各自解释。
- **怎么做**：优先确定批次互击、四种时间域、半开区间与取消不退款；要求跨平台确定性时前置步骤 41 的专项设计。
- **关键伪代码**：

```text
rules = { hitOrder: TickBatch, windows: HalfOpen, cancelRefund: None }
if crossPlatformRequired: require DeterminismDesignBeforeMotor
```

### 01.3 批准首批范围并保留变更记录

- [ ] **做什么**：批准首批范围并保留变更记录。
- **为什么**：文档交付不表示所有代码和第三方依赖都获准引入。
- **怎么做**：确认可开始的步骤及其修改范围，后续规则变化列出受影响步骤。
- **关键伪代码**：

```text
approvedBatch = Confirm(stepIds, ruleVersion)
ChangeDecision -> FindAffectedSteps -> UpdateBaseline
```

## 6. 边界与失败处理

- 缺少目标设备只阻塞性能预算承诺，不妨碍编写纯数据契约方案。
- 若确定性要求升级，运动、碰撞、随机、快照一起重评估，不能只更换时钟。
