# 七大原则与设计模式取舍

日期：2026-10-25；v0.1。本页是针对本框架的设计论证，不按模式数量评价质量。

## 1. 七大设计原则的具体落点

| 原则 | 本框架怎么做 | 如何判断违反 | 避免过度设计 |
|---|---|---|---|
| 单一职责 | FSM许可、动作图选择、时间轴执行、命中仲裁、数值提交、表现各自负责 | 改伤害公式需要改播放器；UI直接改变HP | 按变化原因拆，不把每个小函数都做成System |
| 开闭原则 | 新动作主要加数据；新伤害规则/后端走小策略接口 | 每加怪物都在Runner写类型判断 | 新机制仍可改代码，不承诺任意内容零代码 |
| 里氏替换 | 玩家/AI都遵守意图入口；所有表现后端不得改变模拟结果 | Spine后端独自发伤害事件，Sprite后端没有 | 不支持Mask的后端导出时拒绝能力，不能假装支持 |
| 接口隔离 | 输入源、碰撞查询、表现、规则集分别设小接口 | AI被迫依赖音频/资源/整个GameModule | 内部不需要替换的类无需接口 |
| 依赖倒置 | 战斗核心依赖ICombatQuery/IActionPresentation等契约，TEngine适配器装配 | World内部Resources.Load或操作Canvas | 构造注入即可，首版不为此引入DI容器 |
| 迪米特法则 | 系统读ContextSnapshot/结果，不通过owner.enemy.view.animator找深层对象 | AI通过目标View推导死亡；UI访问命中账本 | 显式数据依赖优于隐藏的全局服务查找 |
| 合成复用原则 | 动作定义+窗口+效果组合；单位由运行数据和系统组成 | Player/Enemy/Boss逐层继承覆盖同一段攻击逻辑 | 既有UIWindow继承继续用；不为反继承而重写框架 |

## 2. 使用的模式与代价

| 模式 | 使用位置 | 收益 | 成本/限制 |
|---|---|---|---|
| Command | IntentCommand、状态请求、动作命令 | 可排队、拒绝、追踪和回放 | 需要回执/过期/去重定义 |
| State | UnitFSM互斥状态 | 统一迁移与许可 | 状态数量膨胀时要拆正交标签 |
| Strategy | RuleSet、伤害公式、部位选择 | 适配StandardACT与SimpleACT | 策略切换固定在开局，避免运行中混合语义 |
| Adapter | 输入、TEngine资源事件、动画后端 | 核心不依赖设备和渲染细节 | 需能力约束及生命周期协议 |
| Observer | 已提交结果通知UI/反馈 | 表现解耦 | 不用它决定权威结算顺序 |
| Composite | AI组合节点/有边界的子图 | 组合复杂决策 | Parallel/Decorator需要独立运行态 |
| Flyweight | 不可变动作与Buff定义共享 | 同类单位不复制配置 | 每单位Runtime不可共享 |
| Object Pool | 已有GameObjectPool与必要缓冲 | 重用View、减少高频分配 | 租用代次、清理、容量和资源所有权 |
| Facade | GameModule.Battle/BattleModule | 统一战斗入口 | Facade不能变成所有技能逻辑的巨类 |
| Factory/Registry | AI任务与命令类型注册 | 可控扩展，避免运行时类名反射 | 新机制需代码注册与构建兼容 |

Pipeline以固定阶段组织，不机械套用“责任链任意处理器”：战斗顺序是规则，不允许插件自行调换伤害与无敌判定。

## 3. 明确不选的重方案

- 不把所有动作做成深继承技能类；已有时序、效果、目标规则优先组合。
- 不为一个单机切片先引入完整DOTS/ECS、网络回滚和DI框架；现有TEngine足够提供基础设施。
- 不把所有事件都保存为完整事件溯源数据库；首版保留可诊断的命令/结果日志和必要快照即可。
- 不把编辑器框架节点直接当运行时战斗对象；导出扁平只读数据避免资产生命周期和执行语义纠缠。
- 不让“减少if”成为目标：许可/窗口/状态边界本来需要判断；避免的是重复事实和散落条件，而非合法的分支本身。

## 4. 维护成本控制

新增第三个相似效果时再评估抽象，必须确认语义、变更方向和生命周期一致。共享“命中后申请效果”合理；把“伤害”“存档”“UI点击”强行统一成一个object[]事件不合理。

公共API写XML用途注释；复杂阶段注释放在逻辑上方；不以try/catch掩盖非法配置。加载失败可以恢复/清理，战斗内容错误必须报告，不静默吞掉。
