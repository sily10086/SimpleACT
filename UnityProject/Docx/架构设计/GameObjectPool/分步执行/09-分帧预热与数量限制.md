## 2. 行为合同

PrewarmAsync(name, targetTotal, token) 表示“补足到目标总数”，不是“再创建 targetTotal 个”，也不是“保证 targetTotal 个空闲”。已有 Spawned/Idle/瞬态占用都计入总量。

目标应为非负整数，不能超过 Capacity 或非零 MaxInstanceCount。非法目标返回 Rejected 并报告原因；不裁剪后报告 Completed。建池时不产生预热请求的情况（`PrewarmCount == 0`）直接算预热完成，没有额外开销。

同池不同调用各自持有完成/取消状态：一个取消不影响另一个。只合并创建工作，不能把每个请求都变成一个独立创建循环。所有请求取消后停止为该池预热，已经建好的实例保留。

**预热是池级空闲过期的阻碍项**（详见[整池空闲过期需求讨论](../GameObjectPool-整池空闲过期需求讨论.md) §3.4）：预热期间不计时，预热完毕即刻开始计时。要点：

1. 用**计数** `_pendingPrewarmCount` 表达阻碍，不用布尔。同池可并发多个请求且"一个取消不影响另一个"，布尔会让第一个请求结束就误判为预热完毕，把计时提前打开。
2. 只在 `0 ↔ 1` 的转换处动作：入队 `0→1` 时把 `IdleStartSeconds` 置 `-1`；终结 `1→0` 时若 `ActiveCount == 0` 则写当前单调时刻。
3. `Completed` / `Rejected` / `Closed` / **`NoProgress`** 都算终结。`NoProgress`（无法增长）必须算结束，否则一个建不出实例的池会永远停在"预热中"、永不过期。
4. 下方 `PrewarmAsync` 中存在 `Total >= target` 的提前返回分支，它**不入队**，因此也没有"预热期间"。该路径要单独续期一次（见 09-A 伪代码），否则会出现"业务刚发起预热、因总量已达标立刻返回，下一个检查点就把这个池销毁了"。

模块/池关闭返回 Closed 或对应的内部取消结果，调用方能区分未完成；外部取消保留标准取消语义。公开结果可精简为 Completed / Rejected / Closed / NoProgress。

## 3. 设计思路

每帧由模块 IUpdateModule 调度，但对每个池施加的是**该池自己的** `PrewarmPerFrame` 上限：轮询到某池时，本帧最多为它创建这么多个实例。这样预热猛的大池不会占满小池的配额，也不需要各池互相迁就一个全局数字。预算统计实际创建尝试，包含随后被同步释放的创建，避免失败无限循环。

预热与建池绑在一起，但方向是**建池带动预热**（2026-10-25 19:20 落地后如此）：`TryGetPoolOrCreate` 同步加载预制体、建后端与容器，池构造函数登记预热，之后的帧里按预算创建实例。建池那一次同步加载不计入每帧创建预算，预算只统计实例创建。未被预热覆盖的池，Spawn 会直接返回"池未建"的明确失败——这属于配置遗漏，不靠改预算或隐式加载掩盖。

创建到目标只承诺某次完成时达到数量。底层过期回收仍可能之后减少空闲数；不后台永久补足，不在预热期间锁住全部对象，也不暂停通用池策略。

## 4. 逐目标伪代码

### 09-A、09-B：入队与合并

~~~text
PrewarmAsync(name, target, token):
  检查外部取消、模块状态和目标合法性
  if (!TryGetPoolOrCreate(name, out pool))      // 同步建池，返回 false 即明确失败
  建池失败 / 取消 -> 返回明确失败，不入队
  await 后核对模块生命周期与池世代，已失效 -> 丢弃
  Total >= target:
    pool.OnPrewarmShortCircuited()   // IdleStartSeconds = -1; TryBeginIdle()
    -> Completed                      // 未入队，需单独续期一次，见 §2 第 4 点
  request = {实际 pool 引用, poolGeneration, lifecycleVersion,
             target, token, 独立 completion}
  pool.OnPrewarmEnqueued()            // _pendingPrewarmCount++；0→1 时置 IdleStartSeconds = -1
  加入该 pool 的请求组
  返回此 request 的等待任务
~~~

请求绑定实际池，不只保存字符串名称。同名重建不会承接老请求。

`OnPrewarmEnqueued` 必须在请求真正进入请求组时调用，不能放在前置校验之前：被拒绝的请求（目标非法、外部 token 已取消）不产生任何预热工作，不应改变池的计时状态。

**请求终结必须统一收口**：无论 `Completed` / `Rejected` / `Closed` / `NoProgress`，也无论从 `UpdatePrewarm` 的哪条分支结束，都要调用一次 `pool.OnPrewarmSettled()`（`_pendingPrewarmCount--`，归零且无借出时 `TryBeginIdle()`）。实现时收敛到一个 `FinishRequest(request, result)`，避免四条分支各写一遍——漏掉其中一条，那个池就永久不过期。

### 09-B、09-C：共享预算推进

~~~text
UpdatePrewarm():
  清理已取消/已关闭/身份失效请求并完成各自结果
  对每组先完成 Total >= target 的请求

  // 每个池的剩余额度独立：本帧对某池最多创建它自己的 PrewarmPerFrame 个
  for 每个有未完成请求的池 (轮转起始点每秒切换，避免固定顺序饿死后面的池):
    budget = pool.Config.PrewarmPerFrame
    while budget > 0:
      desired = 该池仍有效请求的最大 target
      若 pool.Total >= desired -> 完成满足的请求，跳出本池
      if 该池上轮报告过"无增长" -> 本轮跳过，等它状态变化，跳出本池

      before = pool.Total
      budget--
      result = pool.CreateInstance(false)
      // Register(record, false) 可能同步释放，不能直接读旧 record。
      after = pool.Total
      if 创建失败 或 after <= before:
        此池本轮停止，相关请求返回 NoProgress，带明确诊断
        跳出本池

      完成此池中当前 Total 已达到 target 的请求

  // 本帧结束后，对从"有在途请求"变为"无在途请求"的池各结算一次
  for 每个本帧发生请求终结的池:
    if pool._pendingPrewarmCount == 0:
      pool.TryBeginIdle()      // 预热完毕即刻开始计时，不等下一个检查点
~~~

不把某池剩余额度循环浪费在它自己永远无法增长的创建上。外部销毁、回调影响或底层清理造成无增长时结束并报告，避免无限等待启动。

`CreateInstance(false)` 是同步调用，所以不存在"创建进行中"的异步窗口：本帧循环结束后该池要么仍有未完成请求，要么已全部终结。判定点因此可以固定在 `UpdatePrewarm` 尾部，不需要额外的等待或轮询。

**结算不能每帧无条件执行**。如果写成"每帧检查一次该池是否空闲、空闲就写起点"，`IdleStartSeconds` 会被每帧刷新，池永远不会过期，而监控上表现为"已空闲时长恒为 0"。所以必须由"本帧确实有请求终结"这个事件驱动，或依赖 `TryBeginIdle` 内的 `IdleStartSeconds < 0` 守卫把重复写入退化为空操作。

### 09-C：创建不同实例

~~~text
CreateInstance(false):
  直接调用第 04 步 CreateInstance(Idle)
  实例创建只做 Instantiate 池已持有的预制体，不再访问资源模块
  不调用 Spawn / Despawn
  不执行 OnPoolSpawn / OnPoolDespawn
  保持 activeSelf=false，父节点为池节点（不再有 Inactive 容器）
  根据稳定身份确认是否仍保有该实例
~~~

每次创建真实新对象。不能循环 Spawn/Despawn 同一个对象伪造“预热 N 次”。

### 09-D：建池时预热

**没有"启动时遍历配置全部预热"的入口**（2026-10-25 17:00 用户决定，理由见第 03 步 §3）：哪个池被创建，就只预热那个池，用不上的池一个实例都不建。

~~~text
new GameObjectPool(...) 的末尾（第 04 步，2026-10-25 19:20 已落地）：
  if config.PrewarmCount <= 0:
    TryBeginIdle()                        // 空池当场开始计时
  else:
    _pendingPrewarmCount = 1
    module.EnqueuePrewarm(this)           // 只登记，一个实例都不建
  建池同步返回成功，预热在之后的帧里推进

每帧 module.Update：
  for 每个有待推进预热的池（倒序，推完即移出队列）:
    budget = pool.Config.PrewarmPerFrame
    while budget > 0 and Total < PrewarmCount:
      budget--                            // 算创建尝试次数，失败也消耗预算
      before = Total
      CreateInstance(false)
      Total <= before -> 结束预热（无法增长，打警告）
    Total < PrewarmCount -> 下一帧继续
    否则 FinishPrewarm(): _pendingPrewarmCount = 0; TryBeginIdle()

PrewarmAsync(name, targetTotal, token):   // 待实施（第 09 步主体）
  池未建 -> Rejected（不隐式建池）
  否则提交请求并等待结果
~~~

**建池不等预热**（2026-10-25 19:20 决定，覆盖本节早期"预热失败则整池回滚"）：那条要求建池跨帧等预热结算，与第 04 步"建池同步、返回即定论"直接冲突。现在的取舍是——建池只负责加载预制体、建后端与容器、登记预热，返回 `true` 就是"池可以用"；预热失败（无法增长）只打警告并提前结束，池仍然可用，只是实例数不足目标。这样建池点不会因为预热数量大而变成跨帧操作，`TryGetPoolOrCreate` 保持同步语义。

建池内部那次预热与业务调用 `PrewarmAsync` 的差别只有发起者：前者属于建池事务，失败必须让建池整体失败并回滚，否则会留下"池已存在但预热没达标"的半成品；后者是业务主动补足，失败只影响本次调用。两者共用同一份调度与计数，预热阻碍项（`_pendingPrewarmCount`）也统一在一个地方结算。

使用本次调用独有的列表和请求集合，不用跨 await 共享的可变临时字段。根模块 Update 必须在等待期间继续运行；入口用 await，不用阻塞线程的 Wait/Result。

## 5. 数量规则与业务影响

Capacity=0 可借出扩容，但归还后可能立刻销毁，适合明确不缓存的配置；它不允许正数量预热。MaxInstanceCount=0 为不限，与 Capacity=0 不是同一含义。

统一在 TryAcquire 新建分支检查 Max；预热也使用同一“能否创建”的边界。主线程内处理创建请求，不加没有依据的全局锁；异步外部取消仅标记请求状态，由主线程修改容器。
