### 本组采用的设计建议

这些是供后续确认实施的设计，不能冒充已落地事实：

1. GameObjectPoolModule 继承 Module，业务入口为 GameModule.GameObjectPool。
2. 第一版复用 IObjectPoolModule 的单次借出池，普通 C# GameObjectPool 负责 GameObject 的状态及回调。暂不重写通用池，也不引入多种可切换后端。
3. 一个实例记录维护克隆体引用、借出标志（借用 `ObjectBase.Locked`）、实例号与身份；不设归属标记组件，也不预置租约与延时计划。2026-10-25 20:20 删掉了 `PooledGameObject`：外部销毁不再通知池，代价见 04 §6.5。它和可视化 Monitor 是两个角色。
4. 模块只用现有 IUpdateModule 推进各池的预热预算及销毁通知，不重复执行底层池的过期清理。
5. 预热按**每个池自己的** `PrewarmPerFrame` 分帧推进（不是设置级全局预算，避免大池吃满小池配额）；建池走同步加载预制体资产引用（`TryGetPoolOrCreate`），池被创建时若配了 `PrewarmCount` 就在构造函数里登记、由 `Update` 分帧推进，建池本身不等预热；`Spawn`/`TrySpawn` 不隐式建池，未建池返回明确失败；延迟回收保留 UniTask.Delay，用身份和版本保护。
6. 对外查询返回快照，不暴露内部集合；状态修改集中在模块和单池层。

采用复用后端的成本是保留底层容量语义、可能线性查找空闲对象，并处理 Register/Unspawn 可能同步释放记录的边界。若未来实际性能数据要求更换后端，应另列方案；本组不同时设计两套内核。

## 5. 目标结构和职责

~~~text
GameEntry/Settings
  └─ GameObjectPoolSetting（池名 + YooAsset 地址 + 数量与时间参数）
GameApp：启动侧无接线；退出时随 ModuleSystem 逆序关闭
  └─ GameModule.GameObjectPool
       └─ GameObjectPoolModule : Module, IUpdateModule
            ├─ OnInit 读 Settings、建根、发布配置（2026-10-25 17:00 起，无状态机、无显式 Initialize）
            ├─ 配置字典、全实例索引、任务与查询
            └─ GameObjectPool（一个 AssetName 一个逻辑池；建池时按 PrewarmCount 预热）
                 └─ IObjectPool<GameObjectInstance>
                      └─ Object.Instantiate(池持有的预制体)（克隆体不挂任何池专用组件）

GameEntry/GameObjectPoolMonitor（可选）
  └─ Inspector → 查询快照 / 显式调试命令
~~~

运行节点由模块建立，独立于 Monitor：

~~~text
[GameObjectPool]（DontDestroyOnLoad）
  └─ <池名>（每池一个容器，建池时懒创建）
       ├─ 空闲实例（自身 SetActive(false)，父节点不变）
       └─ 已借出实例（无外部 parent 时留在这里）
~~~

第一版不增加 Provider 体系、编辑器窗口、CSV 导出、通用组件自动复位器、对象抢占或自定义资源加载器。

## 6. 核心状态和不变量

实例占用：**只有一个 `IsSpawned` 布尔，没有状态枚举**（2026-10-25 18:10 用户决定，原 Idle → Preparing → Spawned → Returning → Idle 流转图作废）。空闲实例为 false；借出扩容时按占用态注册，注册前即置 true；归还事务期间保持 true（业务可能还在回调里持有它），提交为空闲时才置 false；被外部销毁时摘掉归属（`Marker == null`）并递减占用计数。"是否已注销"不另存标志——`Release` 与 `DetachMarker` 都会摘掉标记，标记为空就是已注销。

- 只有归属明确且租约匹配的记录才能被操作；GetInstanceID 只用于索引，不单独证明身份。
- **借出与归还的对外形状都是 `GameObject`**：`Spawn()` 给出克隆体、`bool Despawn(GameObject)` 收回来，实例记录、租约与底层登记留在池内部（2026-10-25 19:31）。占用计数只在这一进一出里加减，创建本身不动它——否则预热创建会被算成占用。
- OnEnable 发生前先完成父节点、坐标、缩放、回调准备和借出登记。
- 预制体资产引用由池持有，只在池销毁时经 UnloadAsset 归还一次；建池失败不得留下半建池，池释放必须先销毁实例再归还引用；一次 LoadAsset 对应一次 UnloadAsset，多还或少还都是缺陷。
- 建池走同步加载，`Spawn`/`TrySpawn` 不触发资源加载；建池只有一个入口 `bool TryGetPoolOrCreate(string poolName, out GameObjectPool pool)`（有就取、没有就建），不分"查询"与"创建"两个方法，返回 `false` 时 `pool` 为 null。同步路径上不存在"建到一半模块被 Shutdown"的窗口——只有中途抛异常时才会有已取到的引用没人归还，那由调用方按异常处理，不由模块兜底。
- 底层包装 OnSpawn/OnUnspawn 不再控制激活和 Transform。
- Register/Unspawn/ReleaseObject 可能触发同步释放和 MemoryPool 回收；调用后不能继续盲用旧包装记录。
- 销毁先注销，再 Destroy；旧延时和旧销毁通知不能命中新生命周期。
- 查询不创建模块、池或对象；隐藏对象不代表已归还。
- 配置资产不保存运行计数、根节点，也不保存任何"建池进行中"的状态。
- **池级计时只由状态转换驱动**，不由扫描观察驱动：`ActiveCount == 0` 且 `_pendingPrewarmCount == 0` 时，在转换那一刻写空闲起点；任一大于 0 则判定为不可过期。`IdleStartSeconds >= 0` ⇔ 两个计数同时为 0，这条不变式在 Debug 下断言。
- **两个计时概念不得混用**：实例级 `ExpireTime` 依据单对象的 `LastUseTime`（底层 UtcNow），池级 `PoolExpireTime` 依据池的 `IdleStartSeconds`（模块单调秒数）。互不替代、互不写入对方字段。

## 7. 数量与资源边界

| 概念 | 合同 |
|---|---|
| PrewarmCount | 启动希望达到的总实例数；不是永久最低保有量 |
| Capacity | 复用底层的软保留目标；超出时释放可释放空闲对象，不抢占借出对象 |
| MaxInstanceCount | 总实例硬上限，0 不限制；无空闲且达上限时借出失败 |
| PrewarmPerFrame | 逐池字段，该池每帧最多创建数量，不承诺固定毫秒成本 |
| ExpireTime | **实例级**空闲过期时间，底层按单对象 `LastUseTime` 判定；已预热实例之后仍可能被回收 |
| PoolExpireTime | **整池级**过期时间，`0` 为关闭（合法值，不是非法配置）；>0 时池连续空闲达到该秒数后整池释放，配置保留、可懒重建 |
| PoolAutoReleaseInterval | **逐池字段**，该池扫描整池是否该自动释放的间隔，>0；只是扫描频率，到期在下一个检查点生效，不是精确定时器 |
| 预制体资产引用 | 池创建时 LoadAsset 一次并保存返回的 GameObject，随池销毁 UnloadAsset 归还一次；不随实例创建/销毁变化 |
| 释放池 | 销毁实例与运行池并归还引用，默认保留配置 |
| 注销池 | 成功释放运行池后删除运行时配置，不修改 SO |

预热目标高于 Capacity 时，底层可能在注册空闲对象时立即清理。第 02、09 步采用“启动配置拒绝矛盾目标；运行请求明确返回无法保有”的规则，不静默裁剪后声称完成。Capacity=0 允许不保留空闲，但不能预热正数量。该规则属于本次细化后的设计建议。

配置保存的是 YooAsset 定位地址而不是 Prefab 引用：SO 对预制体没有硬引用，是否打进包由采集目录与资源包配置决定。地址无效、预制体不在采集目录或远端包未下载时，池创建明确失败，不回退到 Resources、场景对象或空对象。

资源引用归属池，不归属实例：池创建时调用 IResourceModule.LoadAsset<GameObject>(AssetName) 同步取一次预制体资产引用，保存在池内，实例一律 Object.Instantiate 生成，不逐实例走 LoadGameObject。好处是每个池只有一次引用计数、克隆体不带额外 AssetsReference 组件；代价是配对责任落在池上——提前或者多归还一次会让仍在使用的克隆体掉材质，归一化又会让别的池少一次引用，因此归还只允许发生在池销毁路径，且每个池只执行一次。

加载走同步版本 `IResourceModule.LoadAsset<GameObject>(AssetName)`，返回后立刻 Instantiate（2026-10-25 18:25 用户决定，推翻 13:22 的异步方案）。这样建池不跨帧——`TryGetPoolOrCreate` 返回时要么池已可用、要么已明确失败，没有在途状态要维护，`SpawnAsync` 也随之取消（它原本唯一的作用就是等跨帧建池，同步之后没有可等待的东西）。代价有两条：首次建池会同步读 AB 包，是一次不可控的卡顿，所以 `Spawn`/`TrySpawn` 仍然不隐式建池，建池点由调用方显式决定（启动流程或预热）；以及 WebGL 目标不支持同步加载，那个平台下这条路径不可用。

同一 AssetName 被多个池引用时，每个池各自持有一份引用计数，互不影响；一个池释放只归还自己那一份，不会让另一个池的克隆体失效。"池释放"只销毁该池实例与其持有的那一份引用，不承诺同时卸载整个资产包。

UnloadAsset 的真实语义必须写清，否则会误判内存行为：它不接收句柄，接收的是 LoadAsset 当时返回的那个 GameObject。资源模块用这个引用去自己的资产池反查（AssetObject.Target 就是这个引用，同时充当资产池 _objectMap 的 key），把引用计数减一；计数归零只表示"可释放"，真正的 AssetHandle.Dispose 由资源池策略驱动——默认每 60 秒检查一次，空闲超过 60 秒或总数超过容量 64 时才会释放。所以"池销毁"保证的是引用不泄漏，不保证贴图与网格立刻从内存消失；需要立即收缩时由业务显式调用资源模块的强制释放入口，池层不擅自触发。

热更边界随之改变：预制体在运行时按地址加载，不再由启动期 Settings 直接持有引用，因此原有的"启动期反序列化早于热更程序集"约束不复存在；新的约束是地址必须存在于目标资源包内，第 01、16 步按此核对。

## 8. 设计原则如何落地

- 单一职责：配置、实例生命周期、模块入口、编辑器绘制分别负责一个方向。
- 开闭原则：业务复位通过轻量回调接口扩展，核心不猜测粒子/刚体状态。
- 里氏替换：实现统一公共合同，Try API 的正常失败不能变成隐式创建或资源加载。
- 接口隔离：业务接口与快照类型避免暴露后端容器；不为每个小方法单独建接口。
- 依赖倒置：业务依赖 IGameObjectPoolModule，Runtime 不引用热更 GameModule。
- 迪米特法则：业务不触碰记录、取消源、底层池和根节点管理。
- 合成复用：组合既有通用池，不用 Mono 继承层级承载对象池逻辑。

## 10. 用户补充：数据类型选择规则

本节适用于全部步骤，替代旧历史方案中不符合此规则的类型建议。结构体只承载单纯数据，不承载池管理行为、异步请求生命周期或需要共享身份的对象。

选择顺序：字段建立后不变 → readonly struct；确实需要修改数据或 Unity 字段序列化 → 普通 struct；需要框架继承、稳定共享身份、行为和资源生命周期 → class，并写明原因。

| 类型 | 选型 | 理由 |
|---|---|---|
| GameObjectPoolConfig | 普通 struct | Unity 需要序列化可编辑字段，不使用 readonly 序列化字段；只做 SO 条目，只声明字段，不承载常量与判定 |
| RuntimePoolConfig | readonly struct | 运行期字典的值，字段建立后不变；由前者按值复制，模块拿到即只读 |
| PoolSpawnContext | readonly struct | 每次借出上下文，按值传参 |
| GameObjectPoolInfo / GameObjectPoolInstanceInfo | readonly struct | 查询快照，构造函数一次赋值，无 internal set |
| PoolSpawnResult / 泛型结果 | readonly struct | 成功标志和实例/组件引用，按值返回 |
| 销毁通知、预热目标、编辑器命令数据 | readonly struct | 纯参数快照，不管理请求生命周期 |
| 确有可变需求的纯计数数据 | 普通 struct（必要时） | 修改集合中的值须取出修改后写回，防止只改副本 |
| GameObjectPoolSetting | class | 必须继承 ScriptableObject |
| GameObjectPoolModule / GameObjectPool | class | 行为对象，有持续共享身份和生命周期，不是数据容器 |
| GameObjectInstance | class | 继承 ObjectBase，被现有后端/MemoryPool 按身份持有 |
| GameObjectPoolMonitor | class | 必须继承 MonoBehaviour（原 `PooledGameObject` 已于 2026-10-25 20:20 删除） |
| DelayRequest / PrewarmRequest 内部任务 | class（确有共享状态需要时） | 取消/完成状态被多个执行阶段持有，复制会破坏所有权；纯参数另用结构体 |
| Inspector / WiringTool | 按 Editor 基类或静态工具要求 | 框架扩展与行为，不是纯数据 |

结构体方法采用 PoolSpawnContext context 等普通参数；查询可返回 GameObjectPoolInfo?，缺失用 null 表示。新的结构体接口不使用 in、out、ref，也不引入 ref readonly。既有框架对引用类型的输出参数无需为此批量重构。

结构体不保证“总在栈上”或“绝对零分配”：作为类字段/数组元素时随宿主存放，装箱到 object/接口、某些闭包捕获仍可能分配。避免为数据结构体设计多态接口、转 object、非泛型容器或反复捕获；使用泛型 List/Dictionary 并复用容量。包含 GameObject/string 引用只是复制引用，不复制对应对象。

只读结构体保持小而明确，不为少一次分配把大集合、取消源、委托及业务逻辑塞进一个值类型。集合扩容、实例创建和异步取消源等真实分配仍存在，按需性能验证时分别观察。
