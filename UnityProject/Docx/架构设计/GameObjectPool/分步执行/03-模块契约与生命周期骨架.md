## 2. 公共能力与失败合同

| API 族 | 语义 | 实施步骤 |
|---|---|---|
| `OnInit()` 内读 `Settings.GameObjectPoolSetting` 完成初始化 | 不是公共 API，模块被首次取用时由框架调用 | 03 |
| ConfigCount | 已登记的配置条数 | 03 |
| RegisterPool(config) | 仅注册配置，重复键拒绝 | 03 |
| `Shutdown`（`Module` 基类生命周期，**不在接口里**） | 幂等关闭，框架关闭模块时调用 | 03（运行池释放由 07、11 补齐） |
| Spawn / TrySpawn / SpawnLocal、泛型版 | 世界/局部借出；只对已建池有效，未建池明确失败 | 05 |
| TryGetPoolOrCreate | 同步建池（加载预制体并完成预热）；`bool` + `out GameObjectPool` | 04 |
| TryDespawn / Despawn | 归还当前借出对象 | 06 |
| ClearUnused / ReleasePool / UnregisterPool | 清理语义分离 | 07 |
| DespawnAfterAsync / CancelDelayedDespawn | 安全延迟回收 | 08 |
| PrewarmAsync | 对已建池补足到目标数量；建池时的首次预热也在这一步 | 09 |
| ContainsConfig / HasPool / IsManaged / IsSpawned | 状态查询 | 10 |
| FindPoolInfo / FillPoolInfos / FillInstanceInfos | 按值返回可空只读快照，或填充泛型列表 | 10 |

对池不存在、硬上限、对象不受管等预期失败，只有成功标志的 Try 方法返回 false，携带实例结果的 TrySpawn 返回 Success=false 的结果结构体；Spawn 便利方法失败返回 null 并提供明确诊断。**配置错误在初始化时集中报告，而且一条错就整体不发布**——不跳过坏条目继续，避免出现"一半池能用、一半池静默消失"这种更难查的状态。业务回调抛异常属于执行错误：完成必要回滚后保留异常，不吞掉后返回成功。取消用异步取消语义，不混成"已完成回收"。

涉及返回实例和成功标志的 TrySpawn 按值返回 readonly PoolSpawnResult（泛型版同理），通过 result.Success 表达上述正常失败；不使用输出参数。返回配置/查询数据的结构体也按值传递。模块类因继承 Module 和管理生命周期而保留 class。

建池走同步加载（2026-10-25 18:25 用户决定，推翻 13:22 的异步方案）：`TryGetPoolOrCreate` 内部调 `IResourceModule.LoadAsset<GameObject>(AssetName)`，返回后立刻实例化并预热，全部成功才把池加入可访问字典。加载失败、地址无效、返回空对象一律按建池失败处理，不缓存半成品池，也不用空对象占位。因此 `Spawn`/`TrySpawn` 不触发建池——未建池时返回明确失败，而不是让第一次借出的人替所有人承担首次读 AB 包的卡顿。**预热属于建池，不属于启动**：哪个池被创建，就只预热那个池；模块启动时一个实例都不建。

同步之后 `SpawnAsync` 不再需要：它原本唯一的作用是 `await` 跨帧建池，现在没有可等待的东西。留着它反而会让人以为"异步入口能避免首次加载的卡顿"，那是错的——`LoadAsset` 一样要同步读包。

同步建池没有跨帧失效面：`LoadAsset` 返回到发布之间全是同步代码，中间不会有 `Shutdown`、`ReleasePool` 或池重建插进来（Unity 主线程单线程执行）。所以不需要"`await` 回来再复核世代"这一步，也不需要为它维护任何版本号；入口处也不判断"模块是否已关闭"（2026-10-25 18:57 用户要求删掉这道检查）——关闭后配置字典已经清空，建池会在"没有这个池的配置"处返回，同一条路径上不需要第二个判据。

第一版不为全部 API 建立大量结果枚举；预热因需要区分完成、取消与无法保有目标，可使用单独 PrewarmResult。

## 3. 设计思路

**没有生命周期状态机**（2026-10-25 17:00 用户决定）。模块不做"先创建、再等外部 Initialize"的两段式，`OnInit` 里一次读完配置、建好根，之后一直可用，直到框架关闭它。因此接口里不存在 `State`、`IsInitialized`、`Initialize`、`LifecycleVersion`，也不存在一个只为这两段式服务的 `Setting` 属性——要读配置直接读 `Settings.GameObjectPoolSetting`。

**关闭不进接口**（2026-10-25 17:25 用户决定）。`Shutdown` 是 `Module` 基类的抽象生命周期方法，实现类 `override` 它，由 `ModuleSystem` 逆序关闭模块时调用；`IGameObjectPoolModule` 里不再声明同名成员。理由：在本接口声明一次，等于把框架已经在管的事再说一遍，还会诱导业务侧主动去关一个由框架管理、并且可能被别人正在使用的模块。要主动关整个模块，走框架级入口（`ModuleSystem`），不要拿接口变量去调单个模块。

理由不是"少写代码"，而是这组状态本身不提供保证：调用方先问状态、再执行操作，两次调用之间状态照样可能变，真正的操作入口本来就得各自判一次。现在没有对外状态，也没有一个"配置是否发布"的内部哨兵——`_configs` **始终非空**，初始化失败只是空字典。各入口在"查不到这个池"时返回失败，成功初始化但配置为 0 条时走的是同一条路径。

**配置读取放在 `OnInit` 里是安全的**：`Settings` 是场景里常驻的 MonoBehaviour，用 `FindObjectOfType` 懒查找，不依赖启动顺序；`Settings.GameObjectPoolSetting` 在 `Instance` 为 null 时返回 null 而不是抛异常，正好对应"缺少配置资产"这个失败分支。取不到资产或内容有错时只打错误日志，字典清空后保持为空，不抛异常也不会留下半成品。

**预热改到建池时做**（2026-10-25 17:00 用户决定，覆盖早期的"启动预热全部配置池"）：不是每个配置里的池都会在这一局用到，启动时把 `PrewarmCount` 全建一遍，会把用不上的预制体也拉进内存、把启动时间拉长。现在的规则是——池被创建（`TryGetPoolOrCreate`，第 04 步）时就按该池的 `PrewarmCount` 预热，`PrewarmPerFrame` 仍然分帧推进，`AdvancePrewarmRequests` 仍然在 `Update` 里推进（第 09 步）。因此第 09 步不再提供 `PrewarmConfiguredPoolsAsync` 这种"遍历配置全部预热"的入口。

**不引入世代号，也不判断"模块还开着吗"**（2026-10-25 18:57 用户要求删掉 `_root == null` 前置检查）：建池是同步的，不存在"跨帧回来发现模块关了"这种情况。关闭之后 `_configs` 已经清空，任何建池请求都会在"没有这个池的配置"处返回——这条判据回答的是"这个池现在还能不能建"，比"模块处于什么状态"更直接，也不需要随状态机一起维护。`_root` 只作为容器挂载点存在，不承担状态语义。

模块 Priority 直接内联写成 `public override int Priority => 5`（不设常量），底层 ObjectPoolModule 为 6，利用现有逆序关闭使游戏对象池先释放。实施时读取实际排序与优先级，不依赖名字推断顺序。

## 4. 逐目标伪代码

### 03-A、03-B：初始化与注册

~~~text
OnInit():
  configs.Clear()；root = null；monotonicSeconds = 0
    // 字典从字段初始化器建出来，这里只清空，永远不留 null
  setting = Settings.GameObjectPoolSetting
    // 场景常驻组件懒查找；Instance 为 null 时返回 null，不抛异常
  setting 为 null -> 错误日志（"缺少配置资产"），返回（字典保持为空）
  setting.TryBuildConfigs() -> 失败 -> 错误日志（带首个失败原因），返回
  创建模块常驻根（池各自的子节点由建池时懒创建，不分 Active / Inactive 两层容器）
    // 一句 new GameObject，不包 try-catch：失败没有可挽救的中间态
  configs = buildResult.Configs      // 这是数组，成功分支必非 null
  for i in 0..configs.Length-1:
    _configs[configs[i].PoolName] = configs[i]
      // 构建阶段只挡空池名、不判重（重名只在编辑器诊断里报），所以这里允许同名覆盖：
      // 数组顺序即生效顺序，靠后的条目胜出，条数可能少于条目数
  // 不加载任何资源、不建任何池、不预热任何实例

RegisterPool(config):
  池名为 null/空 -> false（只防公开 API 抛 ArgumentNullException）
  编辑器下：ValidateRuntime(config) 返回文案 != null -> false
  configs.TryAdd(config.PoolName, new RuntimePoolConfig(config)) 失败（重名）-> false
  -> true
  不读资产：配置读取失败时这里照样能登记成功
  不触发建池、不加载资源、不 Instantiate
~~~

模块根由模块独占所有权，业务拿不到引用。**全程不用 `try-catch` / `try-finally`**（2026-10-25 17:15 用户要求）：建根就是一句 `new GameObject`，失败没有可挽救的中间态，把异常交给框架比在原地猜"该回滚到哪一步"更清楚；`Shutdown` 的复位也不套 `finally`，`Destroy` 正常路径不抛，为它加一层保护只是让代码多一道缩进。代价见 6.5。

### 03-B：更新职责

~~~text
Update(elapseSeconds, realElapseSeconds):
  monotonicSeconds += realElapseSeconds      // 池级计时基准，单调、非缩放
  FlushDestroyedNotifications()              // 先清账，保证计数反映本帧真实归还
  AdvancePrewarmRequests(globalBudget)       // 内部在请求终结时结算预热阻碍项
  TryExpireIdlePools(monotonicSeconds)       // 按间隔节流，见第 07 步
  // 不手动再次更新底层 ObjectPoolModule
~~~

三个调用的顺序不能互换：`FlushDestroyedNotifications` 必须先执行，否则本帧被外部销毁的借出对象尚未减计数，池会被误判为"仍有占用"而错过本轮过期；`AdvancePrewarmRequests` 必须早于过期扫描，否则预热刚结束的池会在同一帧被判定为已空闲却带着未结算的阻碍项。

时间源只用 `realElapseSeconds`，不用 `DateTime.UtcNow`：后者受系统校时、时区调整影响，可能出现负间隔或跳过整天；`realElapseSeconds` 不受 `Time.timeScale = 0` 影响，暂停游戏不会让池"看起来空闲了很久"。

池级过期是**内部驱动行为**，不新增公共 API 触发它；手动释放仍走第 07 步的 `ReleasePool` / `ClearUnused`，自动过期只是复用同一个非强制释放入口。

~~~

### 6.2 十二处与早期设计的决定

1. **没有状态机**（2026-10-25 17:00 用户决定）。删掉 `GameObjectPoolModuleState`（`NotInitialized / Ready / Closing`）与依赖它的 `State`、`IsInitialized`，以及 `Initialize`、`LifecycleVersion`、`Setting` 五个成员。理由见 §3：先问状态再操作并不提供保证，各入口本来就得自己判一次。
2. **初始化并进 `OnInit`**（同一决定）。不再是"创建对象 + 显式 `Initialize(setting)`"两段，配置来源固定为 `Settings.GameObjectPoolSetting`。`Settings` 用 `FindObjectOfType` 懒查找，`Instance` 为 null 时返回 null 而不是抛异常，正好对应"缺少配置资产"分支。
3. **预热移到建池**（同一决定）。模块初始化零实例化；第 09 步不再有 `PrewarmConfiguredPoolsAsync`，只有随建池触发的预热与补足。
4. **不建 `Active` / `Inactive` 两层容器**（16:50 用户决定）。场景层级只到"模块根 → 每池一个同名子节点 → 实例"，空闲实例就是自己的 `SetActive(false)`，父节点仍是池节点。原因：池节点已经把实例归拢清楚了，再套一层只会让层级多两级，并且引入一个"空闲实例该在哪个父节点下"的同步状态——借出换父、归还换父、异常路径漏换一次就永久错位。原来的设计还想省一次 `SetActive`（靠父根整棵关掉），但借出时照样要 `SetParent`，省不下什么。
5. **完全不使用 `try` / `catch` / `finally`**（17:15 用户要求，覆盖早期"建根用 try-catch、清理段用 try/finally"的写法）。原先那两处的目的都是"把失败收敛成可处理的状态"，但都不成立：建根只有一句 `new GameObject`，`_configs` 在它**之后**才赋值，所以不存在"配置已发布、根却不在"的半成品可回滚——把异常交给框架，比在方法里猜该回滚到哪一步更清楚；`Destroy` 在正常路径不抛，`finally` 只换来多一层缩进。方法名随之下调：`TryCreateRoot` → `CreateRoot`，不再返回 bool。
6. **`RegisterPool` 对空池名做一次快速拒绝**。发布版没有 `ValidateRuntime`（整段在 `#if UNITY_EDITOR` 里），空池名直接进 `Dictionary.TryAdd` 会抛 `ArgumentNullException`——那是异常，不是 §2 要求的"明确失败"。这一处只挡 `null` 与空串，不复制任何字段规则，完整校验仍然只在编辑器里跑。
7. **不写显式构造函数，也不加 `[Preserve]`**（17:10 用户决定）。原先为了"明确告诉读者这里必须有 public 无参构造"而写了一个空构造 + 类型级 `[Preserve]`，但两者都不产生实际价值：`Activator.CreateInstance` 只认 public 无参构造，而编译器为没有构造声明的类隐式生成的就是 public 无参构造（元数据已验证）；`[Preserve]` 在全工程其它模块里一处都没有，唯一作用是给 IL2CPP 防剥离，而剥离是构建期问题，代码层加特性能缓解但证明不了，统一留给第 16 步的构建检查。
8. **`_configs` 改为始终非空**（17:10 用户决定）。原先用它是否为 null 表示"配置有没有发布成功"，于是 `RegisterPool`、`Update`、`Shutdown`、建池入口每一处都要先判空。现在字段初始化器直接 `new`，`OnInit` 失败只是 `Clear()` 后留着空字典，`Shutdown` 也是 `Clear()`。代价是"空配置"与"配置读取失败"在 `ConfigCount` 上都表现为 0，无法区分——这是有意接受的：与其维护一个要处处传递的哨兵，不如让各入口在"查不到这个池"时返回失败，两者本来就走同一条路径，失败原因由初始化时那一条错误日志承担。
9. **`Priority` 直接内联 `5`**（17:10 用户决定）。只剩一个使用点，包一层常量只是多一跳；底层 `ObjectPoolModule` 也是直接写 `6`，保持一致。
10. **字典在 `OnInit` 里自己建，构建结果只给数组**（17:15 用户决定）。`GameObjectPoolConfigBuildResult.Configs` 从 `Dictionary<string, RuntimePoolConfig>` 改成 `RuntimePoolConfig[]`，`_configs` 由字段初始化器建好后遍历数组填入。字典是"按池名查"的运行期索引，属于模块，配置资产没理由替调用方决定容器；数组还保住资产里的条目顺序（字典不保序，池列表会随哈希码乱跳）。连带补一条空池名挡板：`null` 键会一路进字典索引抛 `ArgumentNullException`。详见 02 步 6.2 第 2 条。
11. **判重不进构建、也不进模块**（17:30 用户决定）。构建阶段原来那个临时 `HashSet<string>(Ordinal)` 已删除，`TryBuildConfigs` 只做「复制 + 空池名挡板」；重名只在编辑器诊断（`GameObjectPoolEditorValidator.CheckPoolName`）里报并标红。因此 `OnInit` 的 `_configs[config.PoolName] = config` 允许同名覆盖：数组顺序即生效顺序、靠后的条目胜出，`ConfigCount` 可能少于条目数。这与"校验只在编辑器"（15:04）同一条口径——发布版不做没人看的检查。`RegisterPool` 仍然拒绝重名：那是"追加一条新配置"的 API 合同，与"批量读资产"不是同一件事。
12. **接口去掉 `Shutdown`**（17:25 用户决定）。原来接口里有一份 `void Shutdown();`，目的是"业务侧主动关闭也走这里"。但实现类的 `Shutdown` 已经是 `Module` 基类抽象方法的 `override`，框架关模块时一定会调到它；接口再声明一次既没有新增保证，又让"模块归框架管"这件事看起来像"调用方也能随手关"。删掉后接口只剩 `ConfigCount` 与 `RegisterPool` 两个成员，`GameObjectPoolModule` 里的 `public override void Shutdown()` 一字未动，行为断言全部照旧通过（测试走的是具体类型，不依赖接口声明）。

### 6.5 风险

- 根节点在 `OnInit` 里创建，而 `OnInit` 由第一次 `GetModule` 触发。运行时这是游戏启动流程，没问题；但**若将来有编辑器工具在非播放模式下调 `GetModule`，会在当前打开的场景里凭空建一个根节点**。目前所有编辑器侧访问都走 `TryGetModule`（不创建模块），所以不会发生。新增编辑器工具时要注意这一点。
- 根节点用 `DontDestroyOnLoad` 跨场景保活。若第 11 步改成挂到 `RootModule` 之下，要换成 `SetParent(parent, worldPositionStays: false)`，否则世界坐标会被父节点影响。
- `DestroyObject` 用 `Application.isPlaying` 二选一：编辑模式走 `DestroyImmediate`。目前唯一的销毁入口是 `Shutdown`，它只由框架关闭模块时触发——接口里没有这个成员，业务侧不会主动调；`GameApp.Release` 实测也没有对应调用点（第 01、11 步已核对），因此运行期这条路径依赖 `ModuleSystem`，Editor 下退出是否会被调到留第 11 步确认；将来若允许在编辑模式关模块，还要确认 `DestroyImmediate` 不会打断 Inspector 绘制。
- **完全不用 `try` 带来的代价**（17:15 明确接受）：① `OnInit` 里 `new GameObject` 若真抛异常（内存耗尽一类），会直接冒到 `GetModule` 的调用方，而不是被收敛成一条错误日志；② `Shutdown` 中 `DestroyObject` 若抛，后面的 `_root = null` / `_configs.Clear()` 不会执行，模块会停在"根已销毁、字段仍指向它"的状态，此时 `_root` 是个 Unity 已判 null 的引用，各入口仍按"查不到池"失败，不会崩，但状态不干净。这两条在 Unity 正常路径上都到不了（`new GameObject` 与 `Destroy` 都不抛），接受的理由见 6.2 第 5 条。
- 配置一条写错会导致**全部池都不发布**（`TryBuildConfigs` 整体失败）。这是有意的（见 §2），但意味着编辑器校验是发布版安全的前提——`GameObjectPoolValidator` 那条"配置错误"的兜底不能去掉。
- **去掉 `[Preserve]` 引入了 IL2CPP 剥离风险**：`GetModule` 用字符串拼出类型名再反射创建，编辑器与 Mono 下没问题，但 IL2CPP + 高剥离级别可能把这个只被字符串引用的类型连同构造函数一起裁掉，表现是运行期"Can not create module"。代码层没有能证明无事的办法，只能到第 16 步用真实 IL2CPP 构建验证；真出问题就在 `link.xml` 里按类型保留，而不是回到给每个模块贴特性的做法。
