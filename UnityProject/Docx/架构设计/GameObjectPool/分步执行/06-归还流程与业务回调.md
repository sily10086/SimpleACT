## 2. 行为合同

外部未知 GameObject、已归还对象、正在归还中的对象均返回 false，不擅自 Destroy。判断借出状态用记录上的 `IsSpawned`，不能通过 activeSelf/activeInHierarchy 判断。

普通业务入口 TryDespawn(GameObject) 操作的是调用时当前租约。它不能替外部未受管理的旧异步回调识别历史借出：需要延迟归还时应使用第 08 步模块 API。若业务以后确实需要跨异步持有租约令牌，再独立扩展公共 lease API。

OnPoolDespawn 发生在停用之前，方便业务清理事件、特效和自己的任务；业务任务不会因 SetActive(false) 自动全部取消。成功回收后调用者不再拥有该对象，不能在成功通知里重新改它。

## 3. 设计思路

先在记录上立起"归还中"标记，再执行任何业务或 Unity 回调，以阻止同一对象重复归还。**这不是第三个生命周期状态**（04 步已删掉 `PooledInstanceState`）：它只是一把防重入锁，不参与统计、不改变占用标志——业务在归还回调里仍持有引用，`IsSpawned` 保持 true，`ActiveCount` 也保持不变。

ReturnCore 是唯一归还入口。延迟回收和 Inspector 都复用它，不分别维护统计。缺组件的“尚未借出准备”回滚走专用窄路径，不伪造业务回收事件。

## 4. 逐目标伪代码

### 06-A：归属入口

~~~text
TryDespawn(gameObject):
  模块不 Running / 对象无效 -> false
  使用 InstanceID 查 allInstances
  核对记录实际 GameObject/marker
  record.IsSpawned == false -> false        // 空闲实例没有可归还的租约
  record 已在归还中 -> false                // 防重入
  return ReturnCore(record, expectedLease = record.LeaseVersion)
~~~

后续延迟任务调用 ReturnCore 时传它捕获的 lease，不能重新读取当前 lease 作为预期值。

### 06-B、06-C：归还顺序

~~~text
ReturnCore(record, expectedLease):
  核对池世代、记录身份、IsSpawned、expectedLease
  capture immutable identity、GameObject、pool
  立归还中标记          // 防重入；占用标志与 ActiveCount 都不动，业务还持有引用
  CancelDelayedPlan(record)

  按约定的缓存顺序调用 OnPoolDespawn
  每个业务回调后检查 identity 仍属于本次归还操作
  若对象已被业务销毁 -> 转第 07 步清账，不访问 Transform

  clone.SetActive(false)
  核对身份与归还中标记（OnDisable 可能重入）
  若当前父节点不是池节点:
    clone.SetParent(pool.Container, false)   // 借出时挂到外部 parent 的，归还搬回自己的池节点
  核对身份与归还中标记（父节点消息可能重入）
  恢复 localPosition=zero、localRotation=identity、预制体初始 localScale
  清占用标志（IsSpawned = false）；记录实例级空闲起点
  ExitActive()    // ActiveCount--；归零且无在途预热时写池级 IdleStartSeconds
  清归还中标记
  backend.Unspawn(record)
  // 此调用可能同步销毁并 Clear record，之后不再读 record。
  return true
~~~

空闲实例**不靠父节点关掉**：回到池容器后只保留它自己的 `SetActive(false)`。这跟"整棵父根禁用"在效果上等价——`GameObject` 自身 inactive 时，它整棵子树的 `Update`、`OnEnable`、动画与渲染全都停——但少了一层"哪个父节点才是禁用态"的状态要同步（见 04 的池容器说明）。

`ExitActive()` 放在**清掉占用标志之后**、`backend.Unspawn` **之前**：归还回调期间业务仍在操作对象，此时不能算空闲；而 `backend.Unspawn` 可能同步释放并 `Clear` 记录，放在它后面会失去可用的执行点（`ExitActive` 本身只动池级计数，不读记录，但顺序仍以标志提交为准）。归还中标记在 `Unspawn` 之前清掉，否则实例若被留作空闲就会永远卡在"归还中"。

这是池级空闲计时**最主要的起点来源**：池内最后一个对象归还的那一刻，从这里开始倒计时。

归还回调顺序建议与准备逆序，形成栈式清理；统一写入接口注释，不依赖 Unity 组件顺序承载跨组件业务依赖。

### 06-D：回调失败与强制收尾

~~~text
OnPoolDespawn 抛出:
  保留首个异常
  尽可能完成其余已进入生命周期的业务清理
  若身份仍有效 -> 通过统一销毁入口丢弃实例
  保证不永久停在归还中
  向调用方传播首个异常，不返回成功
~~~

仅在这类需要恢复状态/释放资源的边界使用异常处理。不在每个简单 getter 或 Try 条件外包裹 try-catch。

若回调中关闭整个池，本次归还只完成与自己身份匹配的清理，不再次归还已经注销的后端记录。

## 5. 计数口径

归还全程只动两处：提交空闲时清掉 `IsSpawned` 并 `ExitActive()`，`ActiveCount` 共减一次。如果 `backend.Unspawn` 立即释放，释放回调再把 `TotalCount` 减一。**归还回调期间不动任何计数**——业务仍持有引用，池在那段时间必须继续被认为"有占用"，否则会被整池过期判成空池。

只有一套计数：

| 计数 | 归属 | 何时变化 | 用途 |
|---|---|---|---|
| `ActiveCount` | 池级计时 | 取到实例时 `+1`（第 05 步）、提交空闲时 `-1`（本步） | 整池空闲过期的阻碍项 |
| `TotalCount` | 底层 `Count` | 注册与释放 | 容量判断、查询快照 |

**没有 Spawned / Returning / Idle 三份实例统计**（2026-10-25 18:10 随 `PooledInstanceState` 一起删除）。实例级只有 `IsSpawned` 一个布尔，快照按它二分（借出中 / 空闲），没有第三个桶。

Debug 下断言 `ActiveCount == 遍历受管记录数出的 IsSpawned 数量`。归还回调期间 `IsSpawned` 仍为 true，所以这个等式在那段时间照样成立——正是它保证池不会在归还回调里被判定为空闲并提前释放。
