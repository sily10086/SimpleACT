## 2. 记录结构与不变量

GameObjectInstance 需要池引用、GameObject/marker、InstanceID、实例身份版本、LeaseVersion、是否借出占用、是否首次借出、首例克隆的初始 localScale、空闲时间、延迟请求引用。预热请求放单池/模块，不塞入每个记录。预制体资产引用只由池持有，实例记录不保存该引用。

**不设生命周期状态枚举**（2026-10-25 18:10 用户决定，原文的 `PooledInstanceState` 六态已删除）：记录只需要回答两个事实——"算不算借出占用"是 `IsSpawned` 一个布尔，"是不是已经注销"由 `Marker == null` 表达。把这两件事打包成一个枚举值，只是让每个读写点先翻译一次，还会诱导后来者以为状态之间有必须遵守的迁移顺序。

GameObjectInstance 必须继承现有 ObjectBase，且是后端占用和 MemoryPool 复用的行为对象，因此使用 class。GameObjectPool 具有稳定身份和清理行为，也用 class。它们不能仅为减少分配改成可复制数据结构体。配置（运行期用 RuntimePoolConfig，只读）与身份通知等纯数据用 struct，普通值参数传递，不以 in/out/ref 传递。

**`GameObjectPool` 持有三个池级计时字段**（不放在 `GameObjectInstance`、不放在 `ObjectBase`、不写进 SO）：

| 字段 | 类型 | 语义 |
|---|---|---|
| `ActiveCount` | int | 当前处于借出占用态的实例数，借出侧唯一真相 |
| `_pendingPrewarmCount` | int | 该池在途预热请求数，预热侧阻碍项 |
| `IdleStartSeconds` | float | 本轮连续空闲起点；`-1` 表示存在阻碍项，判定为不可过期 |

写入只允许经 `TryBeginIdle()`：

~~~text
TryBeginIdle():
  if ActiveCount == 0 and _pendingPrewarmCount == 0 and IdleStartSeconds < 0:
    IdleStartSeconds = (float)module.MonotonicSeconds
~~~

第三个条件 `IdleStartSeconds < 0` 是冗余守卫：已在计时时重复调用不会把起点往后推，将来若有人误在每帧调用，也只会退化为空操作，而不是变成"池永不过期"的隐蔽故障。

`TryBeginIdle` 的调用点只有四处，每处都先把自己负责的条件准备好再调，不各写一份判定：① 构造函数——没有预热的空池，建池即计时；② `Despawn` 在占用归零时；③ `Unregister` 在占用归零时（底层释放或外部销毁）；④ `FinishPrewarm` 在预热结算时。

`IdleStartSeconds` 用负数当哨兵，不用"正数极大值"或 `bool + time` 双字段——"是否处于可过期空闲"和"空闲多久"必须是同一个值的两种读法，分开存会出现标志位与时间戳互相矛盾的中间态。

Debug 下断言不变式：`IdleStartSeconds >= 0` ⇔ `ActiveCount == 0` 且 `_pendingPrewarmCount == 0`。这一条能同时抓出漏减借出、漏结束预热、非转换点重写三类错误。

**没有归属标记组件**（2026-10-25 20:20 用户要求，`PooledGameObject.cs` 已删除）：它原本只做两件事——给克隆体一个反查记录的落脚点、在克隆体被外部销毁时通知池。前者改由模块的实例索引承担（`Despawn` 用 `GetInstanceID` 反查并复核记录绑的正是这个克隆体）；后者直接放弃，代价见 §6.5——池不再替业务发现"克隆体被外部销毁"，改成"借出时绕开死引用"。

索引采用 GetInstanceID，但查询必须复核 GameObject/marker 与记录身份。所有受管实例都登记，包括 Idle；只登记借出对象会让可视化和外部销毁清账失真。

## 3. 后端适配设计

使用 IObjectPool<GameObjectInstance> 的单次借出形式。底层池名用逻辑 PoolName；节点显示名不作为索引。若必须加命名空间前缀避免与其他同类型池冲突，内部后端名和公开逻辑名分开记录。

底层 OnSpawn/OnUnspawn 只保留必要包装行为，不调用 SetActive，不访问 Transform。借出/回收激活顺序分别交给第 05、06 步。

**重要边界：**Register 和 Unspawn 可能因超容量触发 Release，Release 可能回收包装到 MemoryPool。因此它们应作为提交点，之后返回前使用捕获的稳定值或重新查询，不继续访问未经核对的 record。

## 4. 逐目标伪代码

### 04-A、04-D：建池

~~~text
bool TryGetPoolOrCreate(name, out pool):
  pool = null
  池名为空 -> false
  pools 已有该池 -> pool = 它，true（稳态快路径，不读配置、不碰资源）
  configs 找不到 -> false
  // 不判字段合法性：空地址、负数容量等规则只在编辑器侧校验一次，见下
  // 也不判底层重名：由 CreateSingleSpawnObjectPool 自己抛 GameFrameworkException，见下
  prefab = Resource.LoadAsset<GameObject>(config.AssetName)      // 同步
    // 返回值是预制体资产本体，同时是后续 UnloadAsset 的归还凭据
    // 禁止 Destroy / DestroyImmediate，禁止修改其组件与变换
  prefab 为空 -> false（地址无效 / 资源未下载），不缓存半建池
  创建后端 + 本池容器
  new GameObjectPool(module, config, prefab, container, backend)
    // 计时与预热都在构造函数里一次决定，没有"建完再补一步发布"：
    // PrewarmCount <= 0 -> TryBeginIdle()（空池也参与整池过期，起点是建池时刻）
    // PrewarmCount >  0 -> _pendingPrewarmCount = 1；module.EnqueuePrewarm(this)
    //                      预热结束那一刻才 TryBeginIdle()
  加入 pools（入表即发布，之后才可能被查到）
  返回 true
~~~

建池就是资源的加载时机：配置只有地址，第一次 `TryGetPoolOrCreate` 才加载并把返回的预制体引用交给池；建池之后创建实例不再访问资源模块。

**建池后的"时机"全部收在构造函数里**（2026-10-25 19:20 用户要求，删掉 `OnPoolCreated`）。原设计是构造函数只赋字段，模块建完池再调一次 `OnPoolCreated()` 去开启空闲计时。但这一步和"要不要预热"是同一个决定的两面：有预热就不该计时，没预热就该当场计时。分成两处写，等于把"构造函数里已经算好的 `_pendingPrewarmCount`"再按另一套规则解释一遍，两边一旦不同步，池要么提前开始计时（预热还没完就被判过期）、要么永远不起计时（没人记得回来开）。现在构造函数末尾一个分支读完：`PrewarmCount <= 0` → `TryBeginIdle()`；否则 `_pendingPrewarmCount = 1` 并把池交给模块的预热队列，计时等预热结算那一刻才开始。模块侧因此只剩"入表即发布"一个动作，`_pools[name] = pool` 之后没有任何"补一步"的调用。

`_idleSinceSeconds = -1d` 这个初值必须显式写：`TryBeginIdle` 的守卫里有一条"当前不在计时"，字段默认的 0 会让空池那一支判定失败，池就永远不会过期。

**不判底层重名**（2026-10-25 19:02 用户要求，推翻 18:33 的"判重先于加载"）：底层已有同名池只可能是"上一次没清理干净"或别处直接动了 `ObjectPoolModule`，属于程序错误而不是运行期状态；`CreateSingleSpawnObjectPool` 自己会抛 `GameFrameworkException("Already exist object pool '{Type+Name}'.")`，文案带类型与池名，比本层手写一份更全。前面再加一道 `HasObjectPool` 等于把同一个问题回答两次、多养一份自己的错误文案，还得连带维护"重名时不加载、不归还"这套顺序说明。代价：真撞上重名时抛异常而不是返回 null，此前已加载的预制体引用不会归还——与"运行期不重复校验配置"是同一种取舍，不为程序错误长期兜底。

**同步加载，不是异步**（2026-10-25 18:25 用户决定，推翻 13:22 的异步方案）。`TryGetPoolOrCreate` 里走 `IResourceModule.LoadAsset<GameObject>`，返回 `true` 时池必然已发布、返回 `false` 时必然已明确失败，没有"正在建"的中间态。因此整条链路不需要 `async`/`await`、不需要 `CancellationToken`、不需要在途任务登记，也不需要"await 回来再复核模块有没有被关"——这些全部是跨帧才需要的东西，同步路径上它们是零收益的复杂度。

代价必须写清楚：首次建池会同步读 AB 包，是一次不可控的卡顿（时长取决于资源包大小与存储介质）。这正是 `Spawn`/`TrySpawn` 仍然**不隐式建池**的原因——把建池点交给调用方显式决定（启动流程或预热），而不是让第一次借出的人替所有人承担这次卡顿。另一个代价是 WebGL 目标不支持同步加载，该平台下这条路径不可用。

`SpawnAsync` 也随之取消：它原本唯一的作用就是 `await` 跨帧建池，同步之后没有可等待的东西，留着只会让调用方以为"异步入口能避免卡顿"。

**`TryGetPoolOrCreate` 不重复校验配置字段**（2026-10-25 18:29 用户要求）：空地址、负数容量、超限预热这些规则已经由 `GameObjectPoolValidator.ValidateRuntime` 在编辑器侧全量跑过，落点是 `TryBuildConfigs`（编辑器分支）与 `RegisterPool`（编辑器分支）两处入口；发布版跑的正是那份校验通过的数据，在这里再判一遍就是同一条规则的第三个落点。多一个落点的代价不是多几行代码，而是"改规则时漏改一处就静默不一致"——两处判据一旦分叉，谁对谁错要靠读三份代码才能确定。

代价与前文的既有约定一致（运行期只挡"会让公开 API 抛异常"的输入，其余不校验）：发布版若真拿到空地址，`IResourceModule.LoadAsset` 会先判 `string.IsNullOrEmpty(location)` 并抛 `GameFrameworkException("Asset name is invalid.")`，本层不把它转成 null 返回。这是"作者配置错误"而非"业务运行期错误"，让它带着栈直接炸出来比让它变成一个静默的空池更容易定位。`TryGetPoolOrCreate` 的失败合同只覆盖运行时才知道的一种失败——加载不到（返回 null）；底层重名同样交给底层的异常，不在返回值里表达。

**获取与创建是同一个方法**（2026-10-25 18:39 用户要求，合并原 `EnsurePool` 与 `BuildPool`，18:49 定名 `TryGetPoolOrCreate`）：对外只有 `TryGetPoolOrCreate(string poolName)` 一个入口——传池名，有就返回已有的，没有就当场建。拆成"先查再建"两个方法，只会让每个调用点自己拼 `if (查询 == null) 创建()`，把"什么时候建"这个内部决定复制到所有人手里；而且 `BuildPool(RuntimePoolConfig)` 的入参是配置对象，意味着调用方得先自己查配置表，等于把模块的内部结构（配置字典）暴露给外部。合并后池名是唯一入口参数，配置查询留在模块内部。


**池容器**（2026-10-25 16:50 用户决定，取代原先的 `Active` / `Inactive` 两层公共容器）：建池时在模块根 `[GameObjectPool]` 下创建一个与池同名的子节点，该池的**所有**实例——空闲的与已借出的——默认都挂在这个节点下；空闲实例只做自身 `SetActive(false)`，父节点不动。借出时只有调用方显式给了 parent 才换父，归还时若当前父节点不是池容器才搬回来。这样层级是「模块根 → 池 → 实例」三层，每个池一眼能数清有多少实例，也不需要维护"某个实例此刻该在 Active 还是 Inactive 之下"这个额外状态。池销毁时按容器整棵销毁。容器由 `GameObjectPoolModule` 持有的私有字段 `_root` 挂接，因为两者是 `partial` 同一类型，不需要为容器再开一个公开属性。

LoadAsset 返回的是资产本体，既不是副本，也不是句柄：它就是 YooAsset 的 AssetHandle.AssetObject，资源模块同时把它登记进自己的资产池，引用计数置为 1。池对它只允许两种操作——Instantiate 出克隆体、销毁时把同一个引用交给 UnloadAsset 归还。不要 Destroy 它（Editor 下会破坏磁盘资产，且销毁后资产池的反查会永久失败），不要修改它的组件与变换，也不要把它 SetParent 进场景；归还凭据只能是这个原始引用，克隆体或克隆体上的组件都会被资产池拒绝。

### 04-A：借出与归还

~~~text
Spawn():
  backend.TrySpawn(池名) 命中空闲 -> 复用
    命中的记录 GameObject 已失效 -> backend.Unspawn 还回去，当作没命中（完整清账在第 07 步）
  没有空闲 -> CreateInstance(spawned = true)
  取不到记录 -> 明确失败
  record.IsSpawned = true；ActiveCount += 1；IdleStartSeconds = -1
  clone.SetActive(true)
  返回 clone 本身

Despawn(gameObject):
  按实例号查全量索引；查不到 / 不属于本池 / 当前不是借出态 -> 明确失败
  record.IsSpawned = false；ActiveCount -= 1；归零则 TryBeginIdle()
  clone.SetActive(false)
  backend.Unspawn(record)
  返回成功
~~~

**进出都是 GameObject**（2026-10-25 19:31 用户要求）：借出拿到什么、归还就交回什么，实例记录、租约与底层登记全部留在池内部。`ActiveCount` 只在借出/归还这一对入口加减，`CreateInstance` 本身不动计数——因此"建了但没借出去"（预热）不会被算成占用。

归还的顺序不能换：先清占用标志与计数，再 `backend.Unspawn`。底层在总数超过 `Capacity` 时会顺手 `Release` 掉空闲记录，那条记录会立刻走到 `GameObjectInstance.Release`，它读的是"注销前是否占用"——标志还没清就会被扣第二次。

### 04-B：创建与释放记录

~~~text
CreateInstance(spawned):
  Instantiate(池持有的 prefab)，挂到池容器下
  SetActive(false)
  从 MemoryPool 取一条记录，写入所属池、克隆体、实例号、身份
  Initialize(name, 记录自身, locked = spawned, priority)
    // locked 就是借出态：底层用它挡自动释放，与"正被业务占用"是同一件事
  先登记模块索引，再 backend.Register(record, spawned)
    // spawned = true 时底层当场调 OnSpawn -> SetActive(true)
  按实例号与身份复核记录是否还在
  返回记录；已被底层清掉则返回 null

Release(isShutdown):
  捕获克隆体与所属池，清空记录里的引用
  通知所属池注销索引（不碰占用计数）
  若克隆体仍有效 -> Object.Destroy

OnSpawn():
  克隆体 SetActive(true)

OnUnspawn():
  克隆体 SetActive(false)
  position = zero，rotation = identity
  // 克隆体挂在池容器下，position 就是相对容器的局部坐标
~~~

克隆体不带 AssetsReference：这里不走 LoadGameObjectAsync，Destroy 不会自动归还引用计数，资源引用计数的归还完全由池负责（第 07 步）。因此不要给克隆体补挂 AssetsReference，否则会与池的持有关系重复计数。

借出扩容必须直接注册为占用，不能先注册空闲再 TrySpawn；Capacity=0 或超容量时，空闲注册可能立即释放刚创建对象。

**占用计数不进 Release**：底层 `ReleaseObject` 与自动清理都会挡掉 `IsInUse` 与 `Locked` 的记录，能走到 `Release` 的只可能是空闲记录（或关闭池时的强制释放）。计数只在 `Spawn` / `Despawn` 这一对入口加减，`Release` 再扣一次就会变成"多减"。

迁入与 ObjectBase 相同程序集后，override 的访问修饰符应对齐实际基类声明，例如 protected internal override；不能机械复制旧热更程序集中的 protected override。

### 6.2 二十一处与本步早期设计的偏差

1. **`_configs` 与新增的两个字典都是字段初始化器 + `Clear()`，不再在 `Shutdown` 里置 null**。原文写着"字典始终非空"，但 `Shutdown` 里 `_configs = null` 与之矛盾——关闭后 `ConfigCount` 会直接抛 NRE。本步把 `_configs` 改成 `readonly` 字段并在 `Shutdown` 里 `Clear()`，新字典照同一口径。
2. **没有 `try/finally`**（沿用 03 步"不用 try"的口径）。原文要求在 `finally` 里移除 `pendingBuilds[name]`；18:15 之后连这张登记表本身也删掉了（见本条末第 11 条），所以这条约束现在只意味着"每条失败分支靠提前 return 各自归还已经取到的东西"，不依赖任何清理块。同步完成与异步完成两条路径都不留残留状态。
3. **不判断"模块还开着吗"**（2026-10-25 18:57 用户要求删掉 `_root == null` 前置检查）。03 步已删掉 `LifecycleVersion`，本步原先又让 `_root` 兼职状态判据。问题是这条判据永远排在"查配置"前面、却在同一条失败路径上重复回答同一个问题：`Shutdown` 会 `_configs.Clear()`，关闭之后的任何建池请求都会在"没有这个池的配置"处返回，根本走不到挂容器那一步。删掉后 `_root` 只作为挂载点存在。**代价**：关闭之后再用 `RegisterPool` 登记新配置并建池，没有挂载点会抛空引用——那是"先关模块再用模块"的调用顺序错误，不该靠一道长期判断替它兜底（与"运行期不重复校验"同一口径）。

4. **`PooledGameObject` 本步不缓存回调组件**（该组件已于 20:20 整体删除，见第 21 条；回调缓存将随 05 步的接口一起加）。原文 04-C 要求"缓存实际实例的回调实现"，但 `IGameObjectPoolCallbacks` 由 05-C 定义。为没有定义的接口先造字段属于占位，本步只做归属绑定与销毁通知，回调缓存随 05-C 一起加。
5. **实例记录不含"延迟请求引用"**。那是 08 步的延迟回收计划，届时随 `DelayedPlan` 类型一起加字段，本步不预留空引用。
6. **初始 localScale 在记录里，取自"刚实例化完的克隆体"**。原文两处说法（04 记"首例克隆的初始 localScale"、05 记"从池持有的预制体读取"）在这里合并：克隆体此刻还没挂到任何父节点，`localScale` 就等于预制体的值，既满足"每实例一份"，也不需要池再存一个字段。
7. **克隆体在常开的池容器下实例化**，创建后立刻 `SetActive(false)`。原文 §4 写"在禁用 Inactive 容器下 Instantiate"，但 16:50 已决定不要 Inactive 层容器，那条前提不再成立。代价是：预制体本身是激活态时，这次实例化会让它跑一次 `Awake`/`OnEnable`。这与 05 步"准备回调应使用序列化引用或自行保证初始化，不能默认依赖 Awake"是同一条约束，已写进 `CreateInstance` 的注释。
8. **`OnMarkerDestroyed` 只做"索引半程"**（20:20 删掉标记组件后本方法已移除，外部销毁不再通知池，见第 21 条与 §6.5）。原文 04-C 要求"提交给已关联 owner，不当场修改底层容器"，本步照做：摘掉归属标记、注销索引、扣占用计数；从底层移除记录、取消任务、触发业务回调留给 07 步的安全点队列。原因写在那里的注释里——这个回调可能正跑在 Unity 销毁调用栈里。
9. **建池不接收取消令牌**（2026-10-25 18:25 随同步加载一起定）。原文要求"记录调用方 token""取消返回明确失败"，那是 `LoadAsset` 才有的事；`LoadAsset` 是同步调用，没有"取消一个正在进行的建池"这种操作。要中止只能在调用前判断，或干脆不调。
10. **删掉 `PooledInstanceState` 六态枚举**（2026-10-25 18:10 用户决定）。原文用 `None / Preparing / Idle / Spawned / Returning / Destroyed` 描述记录此刻代表什么，实现里真正被读的只有两件事：`Detach` 要不要扣 `ActiveCount`（借出过才扣）、重复的销毁通知要不要忽略（已注销就忽略）。前者改成 `IsSpawned` 一个布尔，后者由 `Marker == null` 判定——`Release` 与 `DetachMarker` 都会摘掉标记，天然构成"已注销"的判据。`DetachMarker` 刻意保留 `Pool` / `InstanceId` / `Identity`，第 07 步的清账还要用它们从底层池里移除记录并复核索引；只有 `Clear` 才把整条记录清空。连带影响：第 06 步归还时的"正在归还"中间态不再是第三个枚举值，而是"占用标志还没清"，语义等价且不需要额外字段。（20:20 起"占用标志"就是 `ObjectBase.Locked`，`DetachMarker` 随标记组件一起删除。）
11. **删掉在途建池登记 `_pendingBuilds`**（2026-10-25 18:15 用户决定，连同 `AwaitBuildAsync` 一起删）。它原本只做一件事——同名并发时让第二个调用 `await` 第一个的任务，省掉一次重复的加载。留着的代价反而更大：建池若抛异常（`CreateSingleSpawnObjectPool` / `new GameObject` / 池构造函数都可能抛），在不写 `try/finally` 的前提下键清不掉，那个 faulted 任务会让该池名之后每次 `Ensure` 都重抛同一个异常，等于永久毒化。**18:25 改成同步加载之后，这个问题连同并发窗口本身一起消失了**——同步调用没有 `await`，第二个调用根本插不进来，`_pools` 复查也成了不可达的死代码，一并删掉。
12. **依赖模块在 `OnInit` 取一次并缓存**（2026-10-25 18:19 用户要求）。原文每次建池都 `ModuleSystem.GetModule<IResourceModule>()`、`ModuleSystem.GetModule<IObjectPoolModule>()`，等于把一次字典查找写在稳态路径上；关闭池时还有第三处。现在两个引用是字段，`OnInit` 最前面赋值，三处共用。位置选 `OnInit` 不选构造函数：`ModuleSystem` 用 `Activator.CreateInstance` 造模块，构造期做框架查询会撞上"模块表还在初始化"；而 `OnInit` 时本模块已经写进模块表，取别的模块只是把它也建出来。赋值放在配置检查**之前**，所以配置缺失时这两个引用也在位，`Shutdown` 这类不读配置的入口不会失效。
13. **建池不判 `AssetName` 是否为空**（2026-10-25 18:29 用户要求）。原文把"空地址"列为建池的一种明确失败，但这条规则已经在 `GameObjectPoolValidator.ValidateRuntime` 里，`TryBuildConfigs` 与 `RegisterPool` 两处编辑器分支各调一次；在建池里再判一遍就是同一条规则的第三个落点，改规则时漏改一处就静默分叉。删掉后发布的代价：空地址会让 `IResourceModule.LoadAsset` 抛 `GameFrameworkException("Asset name is invalid.")`（它在方法开头就判 `IsNullOrEmpty`），本层不再把它转成 null。这与"运行期只挡会让公开 API 抛异常、其余字段规则不校验"的既定口径一致——配置错误属于作者错误，带着栈炸出来比变成静默空池更好定位。
14. **不判底层重名，交给底层抛异常**（2026-10-25 19:02 用户要求，推翻同日晚些时候 18:33 的"判重先于加载"）。18:33 版把 `HasObjectPool<GameObjectInstance>(PoolName)` 摆在建池第一句，理由是重名属于"这一步根本不该做"。但重名只可能来自"上一次没清理干净"或别处直接动了 `ObjectPoolModule`，是程序错误而不是运行期状态；`CreateSingleSpawnObjectPool` 自己就会抛 `GameFrameworkException("Already exist object pool '{Type+Name}'.")`，文案里带类型与池名，比本层手写的一份更全。再多一道判据等于把同一个问题回答两次、多养一份错误文案，还得连带维护"重名时不加载、不归还"这套顺序说明。代价：真撞上时是异常而不是 null，且此前已加载的预制体引用不会归还——与第 13 条同一种取舍，不为程序错误长期兜底。
15. **`TryGetPoolOrCreate` 与 `BuildPool` 合并成一个方法**（2026-10-25 18:39 用户要求）。原设计是两个方法，`TryGetPoolOrCreate(name)` 查到配置后 `return BuildPool(config)`。合并的三条理由：① 对调用方"查"和"建"是同一件事——"给我这个池"，拆开等于把内部顺序复制到每个调用点；② `BuildPool` 的入参是 `RuntimePoolConfig`，意味着调用方得先自己查配置字典，把模块内部结构露了出去，而池名本来就够用；③ 两个方法之间没有任何状态需要传递或保护，拆开只多一层跳转。合并后链路是 空名 → `_pools` 快路径 → `_configs` → 加载 → 建后端与容器 → 发布，6 步在一个方法里顺序读完。方法体约 50 行仍远低于需要拆分提取的复杂度阈值，而"少一个入口"是永久的收益。

16. **签名为 `bool TryGetPoolOrCreate(string poolName, out GameObjectPool pool)`**（2026-10-25 19:04 用户要求，推翻 18:49 版"返回池对象、失败返回 null"）。名字里既然有 `Try`，就该遵守 `TryXxx(..., out T)` 这个全 C# 通用的形状：返回值回答"成没成"，结果从 `out` 走，与 `Dictionary.TryGetValue`、底层 `IObjectPool.TrySpawn(out T)` 保持同一读法，读者不需要先记住"这个 Try 是哪种 Try"。`pool` 在方法第一句就置 null，所以每一条失败分支都不必再管它；调用点写成 `if (!TryGetPoolOrCreate(name, out GameObjectPool pool)) return;`，成功路径直接拿到非空对象。

17. **建池后的计时与预热合并进构造函数，删掉 `OnPoolCreated`**（2026-10-25 19:20 用户要求）。原设计是构造函数只赋字段，模块 `new` 完之后再调一次 `OnPoolCreated()` 开计时。问题是"开不开计时"和"要不要预热"本来就是同一个决定的两种结果：有预热就不该计时、没预热就该当场计时。写成两个方法等于把 `_pendingPrewarmCount` 已经算好的信息在外部再解释一遍，两边一旦不同步，就会出现"预热没完池被判过期"或"没人回来开计时、池永不过期"。现在构造函数末尾一个分支读完：`PrewarmCount <= 0` → `TryBeginIdle()`；否则 `_pendingPrewarmCount = 1` + `_module.EnqueuePrewarm(this)`。模块侧只剩 `_pools[name] = pool` 一步，`TryGetPoolOrCreate` 里不再有任何"建完之后再补一次"的调用。
    **连带把预热提前落地**（原属第 09 步）：`AdvancePrewarm` 按该池 `PrewarmPerFrame` 推进、总数不增长当帧结束、结束后立刻 `TryBeginIdle`。公开的 `PrewarmAsync` / 取消 / 结果体系仍留在第 09 步——这里只做"建池自动预热"这一条路径，不做请求组。

18. **借出与归还收成 `Spawn()` / `Despawn(GameObject)`，同时删掉三个只转发的薄方法**（2026-10-25 19:31 用户要求，参照改造前 `GameObjectPool` 的 `Spawn` / `Despawn` 形状——生成返回 GameObject、回收也接收 GameObject）。原文是 `CreateInstanceForBorrow()` 与 `CreateIdleInstance()` 两个只有一行的包装、`OnInstanceReleased()` 再转一次 `Detach()`、`Detach()` 里再调 `AddActive(-1)`，四层里没有一层真正做判断。现在：① `CreateInstance(bool spawned)` 直接 `internal`，两个调用点各传自己的值；② 释放回调直接调 `Unregister(instance, wasSpawned)`，`Detach` 与 `OnInstanceReleased` 合并成这一个；③ `AddActive` 删掉，`+1` 只出现在 `Spawn`、`-1` 只出现在 `Unregister` 与 `Despawn`，各写一次；④ 新增 `Spawn()` / `Despawn(GameObject)`，调用方借出、使用、归还全程只见克隆体，实例记录、租约与底层登记留在池内部。连带两条行为决定：**占用计数不进 `CreateInstance`**（否则预热创建也会被算成占用，池会永远"有人在用"）；**`Despawn` 必须多判一条 `IsSpawned`**，否则重复归还会把底层的获取计数扣成负数、占用计数多扣一次。




19. **删掉七个纯转发属性，池不再交代自己的家底**（2026-10-25 19:40 用户要求："这些内容根本不需要公开出去"）。被删的是 `Module`、`Config`、`PoolName`、`Priority`、`Backend`、`Container`、`Prefab` —— 它们全部只有一行 `=> _xxx`，唯一作用是把这个池的内部构件端出去。逐个确认过外部读者：`PoolName` / `Priority` 只被 `GameObjectInstance.Create` 用来填 `ObjectBase.Initialize`；`Backend` 只被 `ReleasePools` 用来销毁底层池；其余四个在全工程 **0 处引用**。对应改法三条：① `GameObjectInstance.Create` 增加 `name` / `priority` 两个值参数，由池在创建记录时从 `_config` 里取出来传进去——池名与优先级本来就是底层 `ObjectBase` 的元数据，不是"池对象的能力"，记录不该回读池；② `ReleasePools` 改成按"类型 + 池名"销毁：`DestroyObjectPool<GameObjectInstance>(pair.Key)`，与建池 `CreateSingleSpawnObjectPool<GameObjectInstance>(poolName, ...)` 用的是同一对键，池持有哪个后端实例对关闭没有意义，因此不必交出去；③ 容器、预制体、配置、所属模块全部只留私有字段，类内部直接用字段。
    **刻意保留四个状态读数**（`ActiveCount` / `PendingPrewarmCount` / `IdleStartSeconds` / `TotalCount`）：它们不转发字段，回答的是"这一池此刻什么状况"，读者是真的——模块的预热调度判结束条件、第 14 步监控面板要显示的就是这四个数、验证要断言它们。区别在于它们只读，改状态仍然只能走 `Spawn` / `Despawn` / 预热，外部拿不到任何能改池的东西（拿不到容器就改不了层级，拿不到后端就绕不过计数）。`TryBeginIdle` 同步收成 `private`（只在构造函数、`Spawn`/`Despawn`、`Unregister`、`FinishPrewarm` 里调）。**代价**：验证工程要读容器节点与后端实例只能反射字段（`ContainerOf` / `BackendOf`），这反而成了"外部确实拿不到"的正面证据。

20. **空闲起点改名 `IdleStartSeconds` 并降为 `float`**（2026-10-25 19:44 用户要求）。原名 `IdleSinceSeconds` 读起来像"自……起的秒数"，既不是时间点也不是时长；改成"起点 + 单位"的形状，与模块的 `MonotonicSeconds` 同一套读法。类型从 `double` 降到 `float`：这个值只参与 `now - IdleStartSeconds` 的减法，秒级过期判定用不到 double；单调时钟累计到十万秒（约 27 小时）时 float 仍能分辨约 8 毫秒，远小于最短的过期时间。赋值处因此多一次**显式**转换 `(float)_module.MonotonicSeconds`——写出来是为了让"这里有意丢精度"留在代码里，而不是靠隐式窄化悄悄发生。实例记录里的同名字段一起改（含类型）：池与实例的空闲起点必须是同一单位同一精度，否则第 08 步比较两边时会多一次隐式提升。

21. **实例记录瘦身：删掉归属标记组件与四个字段**（2026-10-25 20:20 用户要求，参照改造前的 `GameObjectInstance`——它只有"克隆体 + 已初始化"两个字段，激活与复位都写在 `OnSpawn` / `OnUnspawn`）。删掉的是 `_marker`（连同整个 `PooledGameObject`）、`_spawned`、`_firstBorrow`、`_initialLocalScale`、`_idleStartSeconds`，替换方式四条：
    ① **`_spawned` → `ObjectBase.Locked`**：底层用 `Locked` 表示"这条记录不许被自动释放"，与"此刻正被业务占用"是同一件事，两个布尔并排存只会多出"占着却可被清理"的中间态。`IsSpawned` 保留成 `Locked` 的别名，`Spawn` / `Despawn` 的读写点不用改字。
    ② **激活、停用与复位搬进 `OnSpawn` / `OnUnspawn`**：底层保证这两个回调与获取计数严格配对（`Create(spawned: true)` 与 `Spawn` 都会调 `OnSpawn`；`Unspawn` 先调 `OnUnspawn` 再减计数），所以池的 `Spawn` / `Despawn` 不必再自己 `SetActive`。坐标复位按改造前的做法：`position = zero`、`rotation = identity`——克隆体始终挂在池容器下，`position` 就是相对池节点的局部坐标。
    ③ **删 `PooledGameObject` 与 `_initialLocalScale`**：`_initialLocalScale` 的唯一用途是"归还时搬回池节点前复位缩放"，而克隆体从头到尾不换父节点，没有"搬回"这个动作。标记组件删掉后，`OnMarkerDestroyed`、`DetachMarker` 与通知携带的身份复核一起消失（`_identity` 保留，模块索引仍靠它复核）。
    ④ **删 `_firstBorrow` / `_idleStartSeconds`**：前者描述的"首次与复用准备顺序不同"在第 05 步才成立，届时按实际差异再加；后者是第 08 步延迟回收的实例级计时，现在没有任何读者。
    **代价**（已写进 §6.5）：外部 `Destroy` 克隆体后池不再收到任何通知。空闲记录会留到下次借出时被绕开（`TrySpawn` 命中但 `GameObject == null`，先 `Unspawn` 归零获取计数再新建）；借出记录被销毁则占用计数残留到池关闭。

### 6.3 后端差异与处理方式

| 事项 | 实际行为 | 处理 |
|---|---|---|
| 建池重名 | `CreateSingleSpawnObjectPool` 遇到同名会抛 `GameFrameworkException` | **不拦**：重名只可能是底层残留或别处直接动了 `ObjectPoolModule`，属程序错误，让底层的异常直接抛出（文案带类型与池名）；本层不再 `HasObjectPool` 预判，也不维护自己的错误文案 |
| `Register` 是提交点 | 总数超过 `Capacity` 时会立刻 `Release()` 掉空闲记录 | 注册后只用捕获的实例号与身份复核（`ContainsInstance`），不把已被清掉的记录当成功实例返回 |
| Capacity = 0 | 空闲注册会被当场释放 | 借出扩容走 `Register(spawned: true)`，占用中的记录不会被释放；行为测试 [19] 覆盖 |
| `Target` 做 `_objectMap` 键 | 销毁后的 `UnityEngine.Object` 参与哈希会失效，键既查不到也删不掉 | `Target` 指向记录自身（纯 C# 对象），行为测试 [15] 断言 `ReferenceEquals(Target, record)` |
| 名称分组 | 底层按 `ObjectBase.Name` 分组，`Spawn(name)` 只在该组里找；无参的 `TrySpawn(out T)` 用的是空名字 `string.Empty` | 所有实例的 `Name` 都取池名，一个池就是一组；**借出必须调 `TrySpawn(池名, out record)`**。误用无参重载不会报错，只会表现为"每次都新建实例、复用从未生效"——测试里的假池也按名字过滤，专门防这一条 |

### 6.5 风险与回退

- 克隆体在常开容器下实例化会跑一次 `Awake`/`OnEnable`。若实测发现业务组件在这两个回调里读到了不该读的状态，回退方案是给池容器加一个"创建期临时禁用"的开关（`_container.SetActive(false)` → 建完再开），但那会连带触发已有子节点的 `OnDisable/OnEnable`，优先级低于要求业务把准备逻辑放进借出回调。
- `ReleasePools` 只把底层池摘掉，预制体引用与业务回调留到 07 步。在那之前单独关闭模块会漏一次 `UnloadAsset`（引用计数不归零，资源池按过期策略回收时仍会释放，只是晚一些）。这是第 07 步的既定范围，不是遗漏。
- 外部 `Destroy` 克隆体后池**收不到任何通知**（2026-10-25 20:20 删掉归属标记的代价）：空闲记录无人清理，会留到底层 `Count` 里，直到下次借出命中它——`Spawn` 会先 `Unspawn` 把获取计数归零再新建，所以调用方不会拿到死引用，但那条记录仍占着 `Count`、仍留在底层。借出中的克隆体被销毁时更糟：`Despawn(已销毁对象)` 直接失败（`TryGetInstance` 里 `gameObject == null`），占用计数残留到池关闭，池因此在关闭前不会再被判成过期。第 05 步加硬上限与泛型借出时，候选判定要沿用"记录仍归属本池 + `GameObject` 有效"这两条，不能只看底层 `CanSpawn`，也不能只看 `IsSpawned`。
- 实例身份版本只在一个池的这次生命内唯一：池被回收后再建同名池，身份从 1 重新开始。第 07 步补池世代后，身份校验要把世代一起带上；在那之前，模块索引的反查靠 `ReferenceEquals(记录里的克隆体, 传入的克隆体)` 兜底——实例号会被新对象复用，只认号不认对象就会把别人的记录当成本次归还的目标。
- **`PrewarmPerFrame <= 0` 会让预热永远推不动**（手改 YAML、合并冲突绕过编辑器校验时）。后果不是卡顿而是"池一直停在预热中、因此永不过期"，且没有日志。当前不做兜底，与"运行期不重复校验配置"同一口径；若需要缓解，最小改动是在 `AdvancePrewarm` 开头把非正预算按 `PrewarmCount` 一次性放行（即保持原有"不缓存"语义），但那等于在运行期又解释了一遍配置规则。
