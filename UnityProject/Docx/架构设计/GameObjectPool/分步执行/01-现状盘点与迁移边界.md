## 6. 盘点结果

### 6.1 基线状态：当前工程整体编译不过是既定前提

本步最重要的结论不是「旧代码写得怎样」，而是**起点本身不成立**。三处独立的缺失让三个程序集同时编译失败：

| 程序集 | 失败原因 | 位置 |
|---|---|---|
| GameLogic | `using GameSingleton;` 指向不存在的命名空间（`Singleton<T>` 实际在 `namespace GameLogic`）；`ConfigSystem.Instance.Tables.TbPoolMap` 在全工程不存在 | GameObjectPoolManager.cs:8、221 |
| TEngine.Runtime | `Settings` 引用不存在的 `GameObjectPoolSetting` 类型 | Settings.cs:37、46 |
| TEngine.Editor | 三个文件引用 6 个不存在的 Runtime 类型（见 §6.4） | 见 §6.4 |

后果有两条必须提前接受：

1. **Unity 在任何编译错误下都不允许进入 Play Mode**，所以第 02～12 步之间「改完就能跑一下」只在引入 §6.4 的隔离后才成立。
2. 后续步骤不是「在可用基线上加功能」，而是**在建类型的同时把基线修回可编译**。第 02 步的 `GameObjectPoolSetting` 一旦创建，`Settings.cs` 的引用立刻成立——它是三个程序集里最先被解开的一环。

### 6.2 01-A：旧实现行为与迁移表

旧实现四文件的实际构成（行数为实测）：

| 文件 | 行数 | GUID | 角色 |
|---|---|---|---|
| GameObjectPoolManager.cs | 807 | 7a701a2468a54b43bf85c2966a5e41ba | 单例入口：配置字典、池字典、实例反查字典、懒建池、Spawn/Despawn 重载 |
| Base/GameObjectPool.cs | 206 | 4d83c0c72bec4c3299fb5e75b8f22c25 | MonoBehaviour，挂在一个空 GameObject 上，作为「单池」 |
| Base/GameObjectInstance.cs | 114 | 6537888746824083b18518895e4d8906 | `ObjectBase` 包装，`OnSpawn` 激活、`OnUnspawn` 隐藏并归零变换 |
| Data/PoolConfig.cs | 21 | acb60a6014eb400a8f6e64bd176709d6 | 普通 class，含 `GameObject Prefab` 硬引用与 `IsCreating` |

**调用方结论：旧实现没有业务调用方。**

- `GameObjectPoolManager` / `GameCommon.GameObjectPoolModule` 只在自身四个文件内出现，`GameObjectPoolManager.Instance` 全工程 0 处。
- `.Spawn(` / `.Despawn(` / `IsClone(` / `GetPoolByName` / `GetPoolByClone` / `HasPool(` 的命中全部落在 `GameObjectPoolManager.cs` 自己内部（581、672、715、729、744、765、786 行），没有第二个文件调用。
- 四个脚本 GUID 在全部 prefab / scene / asset 中 **0 处**引用，只出现在各自 `.meta`。
- 外部 DLL / 反射调用：源码层无证据，但热更 DLL 若以字符串反射调用 `GameObjectPoolManager` 则查不出来，标为**待确认**，不作为删除依据。

因此第 12 步的「旧入口迁移」实际工作量是**删除而不是改写**；真正要迁移的是未来业务对新 API 的首次接入。这一点与文档 §1 预设的「列出调用方并逐个迁移」不同，按实际结果执行。

API 行为映射（旧签名逐条对照）：

| 旧签名 | 新入口 | 调用方必须处理的差异 |
|---|---|---|
| `CreatePool(name, GameObject prefab, capacity, autoReleaseInterval, expireTime, priority)` | `RegisterPool(config)` | 不再传预制体，改 `AssetName`；只登记配置，不建池、不加载；同名直接拒绝，不覆盖已有配置 |
| `TryGetPool`（private，未命中时读 `TbPoolMap` 并 `LoadAsset` 懒建） | `TryGetPoolOrCreate(name, out pool)` | 查询不触发建池；未建池时借出明确失败，不再隐式读表建池 |
| `Spawn(name)`、`Spawn(name, parent)` | `Spawn(name, ...)`（世界） | 旧版不传 parent 时对象挂在池根节点下，传 parent 时**仍写 localPosition**；新 API 必须显式选世界/局部，不能用「有没有传 parent」推断坐标空间 |
| `Spawn(name, Vector3 position)`、`(name, position, rotation)`、`(name, position, parent)`、`(name, position, rotation, parent)` | `Spawn` / `SpawnLocal` 两套 | 旧版四个重载全部写 `localPosition` / `localRotation`，语义只有「局部」一种；新版按名字区分，避免同名不同义 |
| `Spawn<T>(...)`（6 个泛型重载） | `Spawn<TC>(...)` + `PoolSpawnResult` | 旧版失败返回 null、无原因（组件缺失时只打一条日志）；新版用值类型结果表达「池未建 / 达上限 / 组件缺失」 |
| `Despawn(GameObject)` | `Despawn(instance)` | 旧版先 `SetParent(pool.transform)` 再 Unspawn，`OnUnspawn` 把世界坐标与旋转清零、`localScale` 保留上次缩放；新版按租约校验并恢复初始变换 |
| `Despawn(GameObject, delay, Action<GameObject> cb, CancellationToken token)` | `DespawnAfterAsync(instance, delay, token)` | 旧版取消时不回调也不回收，对象永久停在外面的父节点上；新版取消即撤回请求，对象仍归池 |
| `Despawn<T>(T component)`、`(T, delay, cb, token)` | `Despawn(instance)` / `DespawnAfterAsync` | 不再靠「组件 → GameObject → 哈希」反查所属池 |
| `IsClone(GameObject)`、`IsClone(Component)` | `IsManaged` / `IsSpawned` | 旧版归还后即 false，实际语义是「当前借出中」；新版拆成「归本模块管理」与「当前借出中」两个查询 |
| `HasPool(name)` | `HasPool(name)`（只查运行池）+ `ContainsConfig(name)` | 旧版要求配置存在且 `IsCreating`，两个概念捆在一起 |
| `GetPoolByName(name)` | `FindPoolInfo(name)` | 旧版是**有副作用的查询**：未建池时会建池、加载资源、AddComponent；新版查询不得改变运行状态 |
| `GetPoolByClone(GameObject)` | `FindPoolInfoByInstance(instance)` | 旧版把内部 MonoBehaviour 池对象暴露给业务；新版只返回只读快照 |
| `ReleasePool(name)` | `ReleasePool(name, force)` / `UnregisterPool(name, force)` | 旧版释放时顺手删配置，无法只释放不删配置；新版两件事分开，有借出时非 force 拒绝 |
| `OnRelease()`（单例释放） | `Shutdown()` | 旧版不清 `_poolConfigs`；新版幂等，先销毁实例再归还资源引用 |

旧实现中被新设计必须避开的缺陷（逐条来自源码）：

1. **编辑期开关掩盖发布期校验**：`CreatePool` 的参数检查整体包在 `#if UNITY_EDITOR` 内（115–138 行），发布版本接受空池名、空预制体、非正容量。新设计沿用"只在编辑器校验"这个取舍（理由与代价见 02 文档 §3），区别在于**校验不在建池时、而在配置资产上**：内容在打包时已定死，Inspector 会先报错；旧实现的坑是运行期才建池、参数可能来自代码而非资产。
2. **空引用直崩**：`Spawn` 失败返回 null，`DefaultSpawn` 不判空就写 `obj.transform.SetParent(...)`（581–591 行）。
3. **索引键取法混用**：写入用 `obj.GetHashCode()`（594 行），查询用 `clone.GetInstanceID()`（718、787 行）。两者当前取值相同，但依赖 `UnityEngine.Object.GetHashCode()` 恰好返回实例 ID 这一实现细节，语义上不成立。
4. **借出即泄漏**：每次 `DefaultSpawn` 向 `_objectPools` 加一条，只有 `NormalDespawn` 删；漏回收的实例在字典里永久驻留。
5. **懒加载失败未处理**：`TryGetPool` 里 `LoadAsset` 失败仍 `CreatePool(name, null, ...)`（230–233 行），之后 `Instantiate(null)` 抛异常。
6. **双源状态不一致**：`PoolConfig.IsCreating` 与 `_pools` 是两份真相，`ReleasePool` 先 `_poolConfigs.Remove` 再 `_pools.Remove`（185–205 行），后者失败时配置已被删。
7. **释放不彻底**：`OnRelease` 不清 `_poolConfigs`（73–99 行）。
8. **回收不还原缩放**：`OnUnspawn` 只重置 position/rotation（88–91 行），`localScale` 残留。
9. **取消即孤儿**：`DelayDespawn` 捕获 `OperationCanceledException` 后既不回调也不回收（695–699 行）。
10. **池根不随模块生命周期**：`_poolRoot` 在 `OnInit` 里 `DontDestroyOnLoad`，与模块 Shutdown 无对应关系。

> **这条结论已被实测推翻（2026-10-25）**：`GameApp.cs` 实际只有 52 行，`StartGameLogicAsync()` 是空方法，**`StartGameObjectPoolAsync` 根本不存在**，`Initialize` / `PrewarmConfiguredPoolsAsync` / `IsInitialized` 三者在全工程 0 处调用。下面这段代码是当时按"应该长这样"推断的，保留下来是为了说明第 11 步为什么曾经被迫锁签名。2026-10-25 17:00 删掉 `Initialize` / `IsInitialized` / 启动预热之后，这三条硬性要求全部作废：模块在 `OnInit` 里自读配置，预热改由建池触发，`GameApp.cs` 因此可以零改动（见[第 11 步](11-TEngine启动退出接入.md) §2）。

```csharp
GameObjectPoolSetting setting = Settings.GameObjectPoolSetting;
if (setting == null) return false;
IGameObjectPoolModule module = GameModule.GameObjectPool;
if (!module.Initialize(setting)) return false;
await module.PrewarmConfiguredPoolsAsync();   // 无参数，返回值被忽略
return module.IsInitialized;                  // 唯一的失败出口
```

由此得来三条硬性要求：

1. **`PrewarmConfiguredPoolsAsync()` 必须无参、无返回值依赖**。不能设计成"启动侧检查预热结果再决定是否进玩法"——那个检查点不存在。
2. **预热失败必须让 `IsInitialized` 变成 false**。也就是说 `IsInitialized` 的语义不是"Initialize 被调用过"，而是"已完成初始化且预热成功、当前可对外服务"。任一池预热未完成、配置非法、生命周期已失效时都置 false，`return module.IsInitialized` 才能兜住"不降级进玩法"。
3. **启动期的版本失效防护只能在模块内部完成**。GameApp 不读 `LifecycleVersion`，所以 `PrewarmConfiguredPoolsAsync` 内部要自行核对 `LifecycleVersion` 与池世代；`LifecycleVersion` 只作为模块公开状态给 Monitor/调试读取，不作为启动判据。

同一条逻辑适用于 `Shutdown`：它不进 `IGameObjectPoolModule`（2026-10-25 17:25 删除），实现类覆盖的是 `Module` 基类的抽象方法，由框架关闭模块时调用。因此它必须无参、幂等、自行取消内部任务，不依赖调用方传取消令牌——但业务侧没有、也不需要有一个 `module.Shutdown()` 调用点。
