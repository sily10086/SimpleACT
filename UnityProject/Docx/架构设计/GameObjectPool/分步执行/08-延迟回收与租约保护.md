## 2. 时间和返回合同

建议延迟使用真实流逝时间，不受 Time.timeScale=0 影响；在 API 注释写明 ignoreTimeScale=true。若原调用方依赖缩放时间，迁移时显式调整，不暗中保留两种默认行为。

delay < 0、NaN、Infinity 拒绝；delay=0 直接尝试当前租约归还，无需创建定时任务。外部 token 已取消则不修改当前计划，立即返回取消。

同一租约重复计划采用“最新替代旧计划”。立即归还、池关闭、模块关闭、实例销毁会取消关联计划。Canceled 不触发成功回调；成功通知只在本次确实归还后执行一次。回调抛异常不改变已经归还的事实，也不能重新安排回收。

## 3. 设计思路

保护条件至少包含：

1. 模块还开着（`_root != null`；模块级没有世代号，关闭就体现为根被销毁）。
2. 具体 pool 对象与 PoolGeneration。
3. record + marker + 实例身份。
4. 本次 LeaseVersion。
5. 本次 DelayRequest 身份与 PlanVersion。

仅比较 GameObject 是否 null 或 InstanceID 不够；仅比较 LeaseVersion 也不够，因为记录可能清空后被复用，或池释放后同名重建。

只在需要延迟时分配请求/取消源。保留 UniTask 的成熟延迟，不引入全局时间轮。取消源和闭包有成本，不能宣称这一功能零 GC。

捕获身份和参数可用 readonly struct，按值传递。DelayRequest 本身若被记录、等待任务、取消和 finally 共同持有，需保留稳定引用身份并使用 class；它是有生命周期的行为状态，不是纯数据。不要把可复制的 CancellationTokenSource 所有权塞进结构体来伪装无分配。

## 4. 逐目标伪代码

### 08-A、08-B：建立最新计划

~~~text
DespawnAfterAsync(go, delay, externalToken, onSuccess):
  检查 delay、externalToken、模块和当前归属
  capture identity + lease
  delay == 0 -> 立即按 capture 归还，成功后通知
  CancelExistingPlan(record)
  request = 新请求，捕获全部身份和外部取消
  record.PlanVersion++
  record.CurrentDelay = request
  request.deadline = 当前真实时间 + delay
  return RunDelayAsync(request)
~~~

取消旧计划可能触发同步取消延续，替换时不能让旧 finally 清除新计划。

### 08-C：等待与回收

~~~text
RunDelayAsync(request):
  try:
    await UniTask.Delay(delay, ignoreTimeScale=true,
                       cancellationToken=request.Token)
    // 恢复到 Unity 主线程后才能访问 Unity 对象
    request.Token.ThrowIfCancellationRequested()
    if !IsCurrentRequest(request):
      return NotReturned
    success = ReturnCore(request.record, request.lease)
    if success:
      onSuccess?.Invoke(request.capturedGameObject)
    return success
  catch OperationCanceledException 对应本次 token:
    结束为取消，不记录“回收成功”
  finally:
    if record 仍是本次 identity 且 CurrentDelay == request:
      清空 CurrentDelay
    释放仅属于 request 的取消源
~~~

ReturnCore 取消当前计划不应导致已成功归还被重新解释为"没有发生"。先处理 Delay 完成后的归还结果，再进入 finally；不在成功回调之后再次抛 token 取消。

**延迟回收与池级空闲计数的关系**：延迟到期后走的是同一条 `ReturnCore`，`ExitActive()` 已在其中执行，本步**不得**再额外减一次 `ActiveCount`。两个相关语义：

- 计划存在期间，对象仍是 `Spawned` 状态，`ActiveCount` 保持不变，池不会被判定为空闲——这正是期望行为，等待回收的对象仍被业务占用。
- 计划被取消（提前归还、池关闭、实例销毁）时不修改 `ActiveCount`：提前归还会经 `ReturnCore` 正常减一次；池关闭时整个池一起消失，不需要单独减。

### 08-D：统一取消

~~~text
CancelDelayedPlan(record):
  capture currentRequest
  无请求 -> return
  清空记录关联 / 增加计划版本
  currentRequest.Cancel()
  // request 的异步 finally 负责 Dispose；不抢先重复释放。
~~~

外部 CancellationToken 的取消可能来自后台线程。取消回调只发出取消信号，不在那里操作 Transform/池字典；需要触碰 Unity 的后续动作回主线程。具体 UniTask 取消选项按已安装版本 API 落实。

## 5. 必须覆盖的竞态

| 时序 | 期望 |
|---|---|
| A 借出 → 安排延迟 → 提前归还 → B 复用 | A 的任务不能归还 B |
| 同次借出设置两次计划 | 只有最新计划可能成功 |
| 池释放后同名重建 | 老池任务无权操作新池 |
| record 回收到 MemoryPool 再复用 | 旧 finally/通知不能清空新请求 |
| token 取消与到期同帧 | 以执行归还前最后一次身份/取消检查为边界 |
| 成功通知中又借出同对象 | finally 不删除新租约的任务 |
