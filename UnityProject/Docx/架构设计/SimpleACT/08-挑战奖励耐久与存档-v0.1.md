# SimpleACT 挑战、奖励、耐久与存档

日期：2026-10-24；分析稿 v0.1。对应原文 §4.8、§6.2–6.4、§11。依赖 D08、D10、D12–D14、D22–D25、D28。

## 1. 先定义局与重试

| 作用域 | 持有数据 | 建议结束条件 |
|---|---|---|
| Profile | 库存/耐久、设置、种子、难度解锁、奖励与结算凭据 | 退出游戏仍保存 |
| Session | seed/难度/规则hash、挑战集合、已完成领奖标记、重试编号 | 退出当前选图会话或通关结束；需策划确认 |
| Attempt | 一次生命的位置、敌人/补给、连续统计、进度、配装快照、终局状态 | 死亡/通关/明确放弃 |

建议死亡重试：Session挑战和已领奖保留，Attempt世界重建；原文“已击杀的进度保留”暂解释为统计/成果保留，不推导成世界中敌人永久消失。该解释须确认。Profile中保存活跃Session的去重凭据用于崩溃恢复，并不等同允许中途续玩。

## 2. 挑战数据与选择

ChallengeDefinition：id、stylePool、difficultyMask、metricType、threshold、resetPolicy、completionPhase、exclusiveTags、requiredLevelTags、rewardTableId、isEasyGuarantee。

抽取顺序：从可在该地图实现的简单挑战中选1个 → 按难度/风格筛候选 → 排除互斥 → 稳定加权选余项 → 数量不足时报告配置错误或使用批准的保底池。不能悄悄少发槽位。地图提供 supplyCount、reachableSupply、enemyTypes 等能力摘要，防抽到无供给图中的吃补给挑战。

| 指标 | 数据源/统计口径 | 特殊处理 |
|---|---|---|
| 连续滞空 | RunWorld 的空中时钟 | 落地清零；“累计3分钟”名称冲突见D12 |
| 总滞空 | 各段滞空累加 | 如策划确实要累计，使用不同metricType |
| 弹刀计数 | CombatCommitted事件及发生时档位 | 不用事件收到时的最新档位 |
| 时停时间 | active的GlobalTick | 暂停不计，见03 |
| 补给计数 | supplyId集合 | 重叠触发/同物体重复事件不累计 |
| 不吃补给/耐力不见底 | 全程失败标记 + 通关终点 | 不能开局就领奖 |
| 进度25% | 同一个ProgressSystem | HUD和耐久共用定义 |
| 完成5挑战 | 当前槽位最多4，依赖隐藏挑战未定 | 首版不入池 |

挑战系统只对已提交模拟事件更新，不在全局事件回调里重新读碰撞组件。每个challengeInstanceId最多发一条完成事件。

## 3. 奖励取样与幂等

挑战完成1个模组、通关2个模组，品质按难度权重。具体模组在选中品质内如何抽取需表明：建议等权或独立weight列，不把“70/25/5”当每个物品的权重。

交易Key建议：ChallengeReward = SessionId + ChallengeInstanceId；ClearReward = SessionId + ClearSequence（若同Session只允许通关一次，则固定序号）；Durability = AttemptId + Settlement。它们必须持久化，内存bool不能防进程崩溃重放。

```text
ApplyReward(transactionKey, deterministicDraw):
  if profile.appliedTransactions contains key: return previousResult
  items = DrawOnceAndRecord(deterministicDraw)
  next = CloneProfileSnapshot()
  next.inventory.Add(items)
  next.appliedTransactions.Add(key, items)
  next.activeSession.claimed.Add(challengeId)
  PersistAtomically(next)
  PublishRewardCommitted(items)
```

同一持久快照中同时保存“物品到账”和“已领奖凭据”，避免存了一半重复发放。存储失败不能显示“已永久保存”；建议保留待提交状态并重试，在离开结果页前提示错误。为了不冻结战斗，Tick只提交不可变奖励请求，Profile串行队列写盘；若要求掉电瞬间也零丢失，必须更强的写前日志/落盘策略并评估成本。

纯随机不增加隐藏pity；同种子反复开新Session刷奖励是D25经济决策，不能擅自改为真随机掩盖。离线存档校验仅用于损坏检测，不承诺防作弊。

## 4. 耐久与经济

公式仍为原文 max(minCost, progress × progressFactor)，系数引用13-耐久公式表。建议保存整数耐久，舍入（ceil/floor/nearest）是待确认规则；本文不选择隐含舍入。

Progress建议按“本Attempt最大前进距离/可跑总距离”单调不降，防临死向后跑减少耐久；原文也可能意指死亡瞬间位置，所以此项必须确认。Session累计进度不参与新Attempt扣费。通关progress=1。

```text
SettleAttempt(attemptId, frozenResult):
  if settlementReceipt exists: return savedReceipt
  cost = Round(max(minCost, frozenResult.progress * factor))
  for item in frozenResult.loadout:
    if !item.permanent: durability = max(0, durability - cost)
  原子提交耐久、终局结果、通关奖励及各自去重凭据
```

先结束Attempt并拒绝后续死亡事件，再异步存档；同一帧多种死因只选择一个主因记录。挑战奖励请求与结算请求由同一串行Profile队列处理，保证先完成的奖励不会被旧快照覆盖。

经济推导：非永久装备数为n，满局消耗的满耐久当量=n×50/100；n=8才是4个，4个永久+4个消耗品则是2个。死亡70%时是0.35n，不固定2.8。原文经济结论只在其假设下成立，不能据此断言所有新手稳定净亏。起始库存、是否能空槽、不同品质效果与重复物品同样影响体验。

## 5. 存档结构与故障恢复

SaveEnvelope：schemaVersion、contentVersion、revision、payloadChecksum、ProfileData、ActiveSessionLedger。ProfileData存DTO，不存GameObject、Transform、委托或可变Luban对象引用。

建议最小实现为明确DTO + 项目可用JSON序列化器；复杂对象图需求再评估 [Odin Serializer](https://github.com/TeamSirenix/odin-serializer)，不因其通用而预先引入。它的AOT支持也需要适配实际热更类型，不能从README推导本项目已可用。

写入流程：生成新revision快照 → 临时文件 → 完整写完并刷新 → 平台支持的替换/备份提交 → 更新内存已保存revision。恢复时比较主文件/备份完整性，采用最近完整版本；不直接吞异常重置库存。IO异常在此处有真实恢复需求，可明确捕获；不在每个业务函数包try-catch。

设置/配装/领奖保存按同一个队列串行；退出等待有限时间并提示失败策略，不能依赖OnApplicationQuit中的未等待异步任务。强退是否扣本次耐久待D28，已提交奖励不回滚。迁移按schemaVersion顺序运行，先备份，不把旧save当新档反复送初始库存。

## 6. 制作步骤与验收计划

- [ ] 建立Session/Attempt/Profile结构与ID规则，定义重试重置矩阵。
- [ ] ChallengeSystem与配置筛选：可完成性、互斥、保底、计数及终点型挑战。
- [ ] RewardService/DurabilitySettlement：显式取样和凭据，统一串行事务。
- [ ] SaveRepository：版本、临时文件、备份恢复、迁移和错误呈现。
- [ ] 结算UI：展示进度、奖励、逐实例耐久、重试配装错误与保存状态。

未来验收：同事件重复投递不多发；领奖和死亡同帧不回收已领物；连续死亡每Attempt只扣一次；保存中断不产生“有标记无物品”；备份能恢复；永久模组不扣；归零不负数；重试不沿用报废效果。没有运行任何存档故障测试。
