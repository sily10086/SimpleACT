# SimpleACT 分步实施与验收计划

日期：2026-10-24；分析稿 v0.1；读者：程序、主策、制作人。

这是未来实现的执行文档，不是已完成开发的报告。所有代码/资产目标保持未勾选。本次用户授权执行的是分析与文档任务；开始实现时先确定对应步骤和01中阻断项。验收条目只列方法，不代表本次运行测试。

## S0：冻结规则与技术边界

**目标**：避免系统间以不同口径实现同一件事。依赖：01、02、03。

| 目标 | 为什么 | 怎么做与伪代码 |
|---|---|---|
| [ ] D01–D07、D09、D14、D15、D17、D30、D32形成决议 | 影响核心状态机和碰撞方案 | `Decision{id, chosenRule, rationale, affectedDocs}`；同步修改对应文档而非只在聊天确认 |
| [ ] 确定确定性保证范围与碰撞路线 | 固定60Hz不等于跨环境逐帧一致 | `SimulationContract = scope + numericModel + collisionModel + versionPolicy` |
| [ ] 确定单位和时间域 | px/s、帧、玩家0.3倍时钟当前混用 | `WorldSpeed = DesignSpeed / DesignUnitsPerWorldUnit`，每参数标单位 |
| [ ] 明确依赖与许可证版本 | 不直接安装14个参考项目 | 为获选依赖登记tag/commit/license；未选依赖保持“仅参考” |

**阶段输出**：规则决议表、允许使用的依赖清单、最小切片范围。未经确认的核心决策不标完成。

## S1：90秒EASY最小切片

**目的**：证明“想保持滞空”和“落岛是主动保命”。无配装/挑战/掉落经济；基础战斗足以演示高档时停。正式美术音乐不作为前置。

| 顺序与全部修改目标 | 为什么 | 做法/伪代码 |
|---|---|---|
| [ ] S1.1 GameApp、GameModule、GameFlowModule、ConfigModule | 当前只接入对象池，缺业务开局 | 保留池初始化；`await RulesReady; await RequiredViewsReady; ShowMenu()` |
| [ ] S1.2 InputModule与动作映射资产/输入设置 | 键鼠手柄统一命令，不让设备驱动碰撞 | `Sample -> Quantize -> Queue(tick,seq)`；切包/设置纳入该步骤范围 |
| [ ] S1.3 RunModule、RunWorld、Clock、CollisionWorld、PlayerState | 单一权威更新入口 | `Tick(command): StepPhasesInOrder()`；只订阅一个驱动回调 |
| [ ] S1.4 CharacterMotor/Action/Stamina/Tier系统 | 核心循环 | 接地、二跳、蹬墙、攻击、闪避、次数和费用事务；详04 |
| [ ] S1.5 Combat/Enemy/Projectile/TimeStop系统 | 让高档收益成立 | `Collect -> Resolve -> Commit`；分时钟，死亡单次提交；详05 |
| [ ] S1.6 固定LevelDescriptor、占位Run场景、岛/刺/墙/补给/终点 | 先隔离随机生成变量 | 手工90秒路线，所有逻辑几何有稳定ID；`BuildFixedLevel()` |
| [ ] S1.7 Player/Enemy/Projectile/Supply View及池配置 | 逻辑需要可观察表现 | `Bind(entityId); ApplySnapshot(); OnPoolDespawn -> Reset()` |
| [ ] S1.8 RunHUDUI、PauseUI、ResultUI及Prefab绑定 | 看得见耐力/档位、能重试 | `OnRefresh -> Snapshot`；已提交事件刷新；不在UI计算余额 |
| [ ] S1.9 CameraDirector、FeedbackModule占位反馈 | 档位与落岛需要能感知 | 镜头死区/边界、简单颜色和声音；不等待正式材质 |
| [ ] S1.10 最小配置表和加载适配 | 占位参数可集中调整 | `PreloadBytes -> Tables -> FrozenRules`，只建本阶段所需表 |

**制作依赖**：先S1.1–1.3建立接口，再并行制作动作/关卡View；战斗接动作数据，HUD/镜头最后接同一个快照。涉及Unity资产使用项目CLI工作流；不能在本次文档工作中宣称已经绑定。

**未来验收**：动作帧与成本符合占位表；落地清零与分帧回复可观察；0耐力处理一致；时停能操作但不能连锁；不同显示帧率不改变该技术路线承诺的结果。玩法验收必须有真实试玩，不能用自动测试代替“想不想继续飞”。

## S2：EASY完整竖切

前置：S1通过用户要求的验收；D08、D10、D12–D14、D19–D25、D28–D29确认。

| 顺序与全部修改目标 | 为什么 | 做法/伪代码 |
|---|---|---|
| [ ] S2.1 ProfileModule、档案DTO、SaveRepository | 所有永久奖励有统一落点 | `ReadOrCreate -> Migrate -> Validate -> Ready` |
| [ ] S2.2 Session/Attempt边界、稳定ID与事务凭据 | 重试不能重复扣耐久/领同奖励 | `NewAttempt(session); SettleOnce(attemptId)` |
| [ ] S2.3 装备定义/实例、LoadoutService、RuntimeEffectSet | 8槽与局内锁定 | `ValidateLoadout -> Freeze -> BuildEffects` |
| [ ] S2.4 LoadoutUI/InventoryWidget/详情与报废列表 | 用户可管理局外资源 | 拖拽/手柄同一个TryEquip命令 |
| [ ] S2.5 LevelModule、片段数据、生成器、G1–G7、保底图 | 满局生成可玩且可复现 | `Generate(seed) -> ProveRoute -> PlaceThreats -> Report` |
| [ ] S2.6 片段导出工具与关卡报告工具 | 策划能制作且知道失败原因 | `EditorGeometry -> StableDefinition`，Editor代码留GameEditor |
| [ ] S2.7 ChallengeSystem、可完成性摘要、抽取配置 | 挑战保底和互斥落地 | `ChooseEasy -> Filter -> FillSlots -> TrackCommittedEvents` |
| [ ] S2.8 RewardService、DurabilitySettlement、串行存档队列 | 实时奖励/终局成本保持一致 | `Transaction(key): mutate copy + receipt -> atomic save` |
| [ ] S2.9 ResultUI扩展、保存状态、报废重试处理 | 避免用户以为没保存或仍能用报废物 | `Receipt -> Display; Restart -> RevalidateLoadout` |
| [ ] S2.10 补齐原14表的必要字段/难度EASY行 | 配置与规则一体化 | 外键、范围、占位状态检查；不手改生成代码 |

**闭环**：菜单→配装→生成→运行→挑战发奖→死亡/通关→耐久与奖励结算→配装/重试。失败处理也属于完成条件：生成失败、资源失败、存档失败必须能解释并恢复。

**未来验收**：反复重试同Session不重抽挑战；同一挑战重复通知仅到账一次；永久模组不消耗；保存失败不假报成功；报废物不能进入新Attempt；地图安全路径成立。强退策略按决议验证，不自行加入惩罚。

## S3：四难度、种子与竞速

| 修改目标 | 为什么 | 做法/伪代码 |
|---|---|---|
| [ ] DifficultyRules与解锁规则 | 四难度共用机制，避免复制四套逻辑 | `Resolve(difficulty) -> ruleReferences` |
| [ ] 各难度片段池、敌人前摇、挑战/掉落池 | 原文难度四联动及掉落差异 | 数据驱动并检查可完成性 |
| [ ] SeedCodec/SeedLibraryUI/Profile种子记录 | 输入、保存、重赛、分享短字符串 | `Parse -> VersionCheck -> BuildRunDescriptor` |
| [ ] ReplayRecorder/Reader、状态hash与差异报告 | 复现承诺需要证据 | `descriptor + inputCommands -> replay -> firstDiffTick` |
| [ ] 成绩记录与比较条件 | 不同装备/规则不能混为同榜 | key含规则/难度/配装，计时口径按D18 |
| [ ] 生成与耐力收支分析工具 | 高难度可能反而续航更强 | 离线采样报告；不得以工具推导替代试玩 |

**未来验收**：同seed/版本/初态重放一致；规则版本不兼容有提示；Cosmetic随机不改掉落；所有难度有可玩回退地图。跨机器复现需指定设备和构建组合，未验证不能承诺。

## 共同实施规则

每步开工前列出对应代码、配置、Prefab/场景和调用方；完成一项目标才勾选，并写实际修改路径。若范围变化，同步修改此表。局部代码变更不顺手重构UIModule或整个框架；不为每个数据类加无意义接口。Unity资源由合法工具制作，不手写生成绑定。

本文件中的所有验收仍为计划。没有运行编译、测试、Unity场景、存档故障模拟或生成器采样。
